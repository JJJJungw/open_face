# service — HTTP API · 웹 UI · 운영 지표

코어를 감싸 서비스로 만드는 층. 큐, 작업 상태, 오류 분류, 화면이 여기 있다.

```bash
uvicorn face_anonymizer.service.server:app --host 127.0.0.1 --port 8000
```

---

## 요청 한 건이 흘러가는 순서

```
POST /api/jobs
   │
   ├─① 무엇이 왔는지 판별      업로드 파일 / s3_keys / s3_prefix
   ├─② 파라미터 확정           기본값 위에 보낸 것만 덮고 검증
   ├─③ 폴더 펼치기             프리픽스 → 영상 키 목록
   ├─④ 중복 제거               폴더와 낱개가 겹치면 한 번만
   ├─⑤ 이미 된 건 걸러내기     결과 버킷과 대조
   ├─⑥ 받을 수 있는 상태인가   모델 준비 · 디스크 여유
   └─⑦ 큐에 넣기               작업 디렉터리 + job.json + 워커에 제출
   │
   ▼
202 {accepted: [...], rejected: [...], queued: N}
   │
   ▼
워커가 한 건씩 ──▶ 내려받기 ──▶ 처리 ──▶ 올리기 ──▶ done
                                  │
                                  └─ 실패 ──▶ 재시도 판단 ──▶ queued 또는 failed
```

### ① 무엇이 왔는지 — `server.create_jobs()`

**제출 진입점은 이것 하나다.** 한 건이든 여러 건이든 폴더든 같은 요청, 같은
응답. 진입점을 나누면 클라이언트가 경우마다 분기해야 하고 화면에도 버튼이
그만큼 늘어난다.

```
multipart/form-data   file=@clip.mp4            업로드 한 건
application/json      {"s3_keys": [...]}        고른 파일들
application/json      {"s3_prefix": "kbs/"}     폴더 하나
application/json      {"s3_prefix": ["kbs/","mbc/"]}   폴더 여럿
```

파일과 폴더는 **같이** 보낼 수 있다. 화면에서 파일 두 개와 폴더 하나를 한꺼번에
체크하는 게 자연스럽기 때문이다. 업로드만 S3 선택과 배타적이다 — 올라오는
바이트와 버킷의 키는 아예 다른 경로다.

### ② 파라미터 확정 — `resolve_params()`

`config.JOB_DEFAULTS` 위에 보낸 값만 덮는다. **API 는 입력만 주면 된다** —
지금 기본값이 곧 운영 설정이라, 호출하는 쪽이 파라미터를 알 필요가 없다.
범위 검증도 여기서 한다(`conf` 0~1, `imgsz` 320~2048, `height` 0 또는 144~4320,
비트레이트 표기 `3500k`/`3.5M`/`3500000`).

### ③ 폴더 펼치기

프리픽스는 **서버에서** 펼친다. 클라이언트가 목록을 먼저 받아 오면 그 사이에
파일이 늘거나 줄 수 있고, 왕복도 한 번 더 든다.

영상 확장자만 고르고, **이름이 `_deid` 로 끝나는 결과물은 뺀다.** 결과물이 입력
폴더에 섞여 있으면 모자이크 위에 모자이크가 한 번 더 올라간다.

### ④ 중복 제거

`dict.fromkeys` 로 합친다. 순서는 유지한다 — 화면에 보인 차례대로 큐에 들어가야
진행 상황이 읽힌다.

### ⑤ 이미 된 건 걸러내기

`skip_processed` 가 켜져 있으면 결과 버킷을 **한 번** 나열해 대조한다. 객체마다
HEAD 를 날리면 폴더 하나에 수백 번 왕복한다.

폴더든 낱개든 **같은 규칙**이 걸린다. 체크박스 하나가 어떤 때는 먹고 어떤 때는
안 먹으면 그건 설정이 아니라 함정이다. 걸러진 건은 조용히 빼지 않고 건별
사유(`409 already_processed`)로 돌려준다 — 눌렀는데 아무 일도 안 일어나는 것이
사용자가 겪을 수 있는 최악이다.

### ⑥ 받을 수 있는 상태인가 — `check_admission()`

모델이 준비됐는지, 디스크 여유가 `FA_MIN_FREE_MB` 이상인지 본다.

**대기열은 개수로 막지 않는다.** 폴더 하나에 수천 건이 정상이고, 개수는 애초에
잘못된 기준이다 — 10건이 50MB 짜리면 아무것도 아니고 2GB 짜리면 이미 위험하다.
진짜 제약은 디스크다.

### ⑦ 큐에 넣기 — `worker.enqueue()`

작업 디렉터리를 만들고 `job.json` 을 쓰고 워커에 제출한다.

**한 건이 거절돼도 나머지는 받는다.** 수백 건 중 키 하나가 오타라고 전체를
되돌리면 호출하는 쪽이 무엇이 들어갔는지 알 수 없다. 다만 **하나도 못 받았으면
202 를 주지 않는다** — 단건이면 그 사유가 곧 응답 코드다(`415`, `409` …).

### 워커 — `worker.run()`

큐에서 꺼내 `running` 으로 바꾸고 시도 횟수를 올린다. S3 입력이면 여기서
내려받는다(대기 중에는 디스크를 쓰지 않는다). GPU 는 파일 락으로 직렬화한다 —
프로세스를 여러 개 띄워도 한 번에 한 편이다.

파이프라인은 프레임마다 진행률 콜백을 부른다. **취소는 이 콜백에서만 끊을 수
있다.** 예외를 던지면 다음 프레임으로 넘어가지 않고 빠져나온다. 진행률은
0.5초 간격으로만 디스크에 흘려 쓴다(초당 수십 번 쓰면 디스크가 탄다).

끝나면 결과를 올리고 `done` 으로 남긴다.

### 실패했을 때 — `worker.fail_or_retry()`

오류를 종류로 가른다.

- **같은 결과가 나올 오류**(깨진 파일, 잘못된 인자, 없는 파일)는 **재시도하지
  않는다.** 세 번 돌려도 결과가 같고, 그동안 뒤에 쌓인 정상 작업이 밀린다.
- **일시적일 수 있는 오류**(S3 네트워크, GPU 메모리)는 `FA_MAX_ATTEMPTS` 회까지
  다시 큐에 넣는다. 소진되면 `failed`.

어느 쪽이든 **어디서 넘어졌는지**(내려받기·변환·검출·렌더)와 **왜 그렇게
끝났는지**(재시도 안 함 / 소진)를 오류에 같이 남긴다. "3회 시도" 라는 숫자만
있으면 그게 많은 건지 적은 건지 알 수 없다.

## 의존 방향

```
config  ←  jobs  ←  worker  ←  server
```

화살표가 한 방향이다. `worker` 는 라우트를 모르고, `jobs` 는 워커를 모르고,
`config` 는 아무것도 모른다. 이게 지켜져야 **워커를 갈아끼울 수 있다** —
AWS Batch 를 붙일 때 `worker` 만 바꾸면 라우트도 상태 코드도 그대로다.

전역 상태는 소유자가 하나씩이다(작업 목록은 `jobs.JOBS`, 워커 상태는
`worker.current`). 쓰는 쪽은 **모듈째로 임포트해 속성으로 읽는다**
(`from . import jobs` → `jobs.JOBS`). `from .jobs import JOBS` 로 가져오면 이름을
복사해 바인딩하는 것이라, 나중에 누가 바꿔도 옛 것을 본다.

## 재시작하면 어떻게 되는가

기동할 때 중단된 채 남은 작업을 정리한다(`worker.resume_orphans()`).

- **수행 중이던 것** → 실패. 중간에 끊겨 결과물이 온전한지 알 수 없다.
- **대기 중이던 것** → 다시 큐에. 아직 아무 일도 일어나지 않았으므로 그대로
  다시 돌리면 된다. 이때 **시도 횟수는 올리지 않는다** — 재시작은 그 작업이
  실패한 것이 아니고, 여기서 세면 배포 세 번에 재시도가 소진된다.

`--workers N` 으로 여러 개를 띄운다면 `FA_RECOVER=0` 으로 **한 프로세스만
켜 두어야 한다.** 여럿이 켜면 각자 같은 작업을 재큐해 중복 처리한다.

## 로컬 디스크는 어떻게 비우는가

S3 작업은 결과를 버킷에 올린 뒤 **로컬 사본을 바로 지운다.** 다운로드 라우트가
"로컬에 없으면 S3 로 302" 이므로 잃는 것이 없고, 안 지우면 대량 처리에서
디스크가 먼저 찬다. 최종 실패한 작업도 `job.json` 만 남긴다 — 원인 파악에 쓰는
것은 사유·단계·시도 횟수뿐이다.

**직접 업로드분은 지우지 않는다.** 로컬이 유일한 사본이라 지우면 결과가
사라진다. `FA_KEEP_LOCAL_RESULT=1` 로 S3 쪽도 예전처럼 남길 수 있다.

## 작업 상태가 디스크에 있는 이유 — `jobs.py`

메모리 dict 에만 두면 (a) 재시작 시 전부 사라져 폴링 중인 클라이언트가 404 를
받고, (b) `--workers 2` 로 띄우는 순간 업로드는 A 프로세스, 폴링은 B 프로세스로
가서 계속 404 가 난다. 작업별 디렉터리에 `job.json` 을 두면 둘 다 해결된다.
메모리의 `JOBS` 는 캐시이고 진짜 원장은 디스크다.

## 오류 — `errors.py`

RFC 9457 `application/problem+json`. 사람이 읽는 문구와 별개로 `code` 가 안정된
식별자이고, `retryable` 로 서버가 판단을 대신 내려 준다. 전체 목록은
`GET /api/problems` 로 볼 수 있다(31종).

## 지표 — `metrics.py`

큐 대시보드가 공통으로 보여 주는 것들이다. 그중 **대기 지연**(가장 오래 기다린
건)이 핵심이다 — 깊이만 보면 "1분에 빠지는 100건" 과 "두 시간째 멈춘 3건" 이
같아 보인다. 여기에 이 서비스에만 있는 **폴더별 진척률**을 더한다. 나머지는
전부 "지금 큐에 있는 것" 만 말해 주는데, 데이터셋을 통째로 돌릴 때 궁금한 건
"전체 중 얼마나 남았나" 이고 그건 큐가 아니라 버킷에 있다.

## 파일

| 파일 | 하는 일 |
|---|---|
| `config.py` | 환경 변수와 처리 기본값. 아무것도 임포트하지 않는다 |
| `jobs.py` | 작업을 만들고 디스크에 남기고 다시 찾고 정리한다 |
| `worker.py` | 큐에서 한 건씩 꺼내 처리. 재시도·취소·GPU 락·복구. **HTTP 를 모른다** |
| `server.py` | FastAPI 앱과 라우트 |
| `errors.py` | RFC 9457 오류 31종 |
| `metrics.py` | 큐 지표와 폴더별 진척률 |
| `webui.py` | `static/index.html` 로더 |
| `static/index.html` | 화면 전부. HTML·CSS·JS 한 파일, 빌드 도구도 CDN 도 없다 |
