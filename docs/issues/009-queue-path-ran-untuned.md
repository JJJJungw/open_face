# 009 · 큐 워커가 튜닝 안 된 기본값으로 돌고 있었다

**상태** 해결됨 (재측정 대기)

**한 줄** 잡 페이로드가 말하지 않은 처리 파라미터를 아무도 안 채워서, 큐 경로가
**`batch_size=1`, `imgsz=960`** 으로 돌았다. 웹 화면은 32/1280 을 쓴다. L40S 에서
GPU 사용률 20%, GPU 메모리 721 MiB — 45GB 짜리 카드를 거의 안 쓰는 상태였다.

## 증상

EC2 에서 한 편 처리 시간을 실측했다. 720p 34초짜리 영상에 **49.5초**, 실시간 대비
0.70배. L40S 에서 나올 숫자가 아니다.

단계별로 쪼개 보니 더 이상했다.

```
검출(GPU)              15.2s   30.8%
인제스트(디코딩·전사)     13.5s   27.4%
모자이크·중간파일 쓰기     11.3s   22.9%
최종 H.264 인코딩·먹싱     8.8s   17.9%
추적·보간                0.4s    0.9%
GPU 31%  ·  CPU 69%
```

돌아가는 중의 GPU 를 2초 간격으로 찍었다.

```
0 %, 721 MiB      ← 인제스트 (CPU)
20 %, 721 MiB     ← 검출 구간. 여기서조차 20%
20 %, 721 MiB
0 %, 721 MiB      ← 렌더·인코딩 (CPU)
```

**검출 구간에서조차 GPU 가 20% 다.** GPU 가 한계인 게 아니라 굶고 있었다.

## 재현

큐 경로로 잡을 하나 넣고 `nvidia-smi -l 2` 로 메모리를 본다. 721 MiB 면 배치가
1이다. 웹 화면으로 같은 영상을 넣으면 5.2 GB 를 쓴다 — **같은 코드, 같은 GPU,
같은 영상인데 다르다.**

## 원인

기본값이 두 벌 있었다.

```python
# core/pipeline.py — 함수 시그니처
def process(self, ..., imgsz=960, ..., batch_size=1, ...)

# service/config.py — 서비스가 튜닝해서 들고 있던 값
JOB_DEFAULTS = {"imgsz": IMGSZ(1280), "batch_size": 32, ...}
```

웹 화면은 `JOB_DEFAULTS` 를 요청에 실어 보낸다. 큐 워커는 **잡 페이로드에 적힌
것만** 파이프라인에 넘겼다.

```python
for k in ("method", "conf", "imgsz", "batch_size", ...):
    if t.get(k) is not None:
        p[k] = t[k]          # 없으면 안 넣는다 → 시그니처 기본값으로 떨어진다
```

시그니처 기본값은 **"안전한 최소값"** 이다. 노트북에서 CLI 로 한 편 돌릴 때
메모리가 터지지 않을 값이지, 우리가 GPU 서버용으로 고른 값이 아니다.

새 진입점을 만들면서 "페이로드가 말한 대로 처리한다" 는 규칙만 세웠고, **말하지
않은 것을 무엇으로 채울지**는 정하지 않았다. 그러면 언어의 기본값이 정책이 된다.

## 영향

한 편 49.5초, 시간당 73편. 이 숫자로 저쪽에 워커 수와 KEDA 설정을 요청할
뻔했다. **297편짜리 폴더 하나가 4시간 5분**이고, 세 폴더면 12시간이다.

더 나쁜 것은 그 판단이 **GPU 를 더 사라**는 방향이었다는 점이다. GPU 가 31% 만
쓰이는 프로파일에서 GPU 인스턴스를 8대로 늘리면, 늘린 8대가 똑같이 69% 를 논다.

그리고 이건 **품질에도 영향**이 있다. `imgsz` 가 960 이면 1280 으로 튜닝한
검출률이 아니다. 큐로 처리한 결과물과 화면으로 처리한 결과물이 **다른 영상**이
된다 — 그게 제일 무섭다.

## 해결

**기본값을 한 벌로 만든다.** `face_anonymizer/params.py` 를 새로 두고 서비스와
큐 워커가 같이 쓴다.

```python
# params.py — 단일 출처
DEFAULTS = {"imgsz": IMGSZ, "batch_size": BATCH_SIZE, ...}
JOB_OVERRIDABLE = ("method", "conf", "imgsz", "batch_size", ...)

# service/config.py
JOB_DEFAULTS = dict(params.DEFAULTS)

# job_runner.py — 잡이 말하지 않은 자리를 채운다
p = {k: v for k, v in params.DEFAULTS.items() if k in params.JOB_OVERRIDABLE}
for k in params.JOB_OVERRIDABLE:
    if t.get(k) is not None:
        p[k] = t[k]
```

**잡 페이로드는 "다르게 하고 싶은 것만" 적는 자리**가 됐다. 전부 적어야 하는
계약이면 적는 쪽이 우리 튜닝값을 알고 있어야 하는데, 저쪽이 그걸 알 이유가 없다.

`JOB_OVERRIDABLE` 로 덮어쓸 수 있는 키를 명시한 것은 별개의 이유다. 임의의
파이프라인 인자를 페이로드로 넘기게 두면 계약이 없는 것과 같다.

### 걸린 것 — 기본값을 채우니 CRF 분기가 죽었다

```python
if "crf" in p and "bitrate" not in p:     # 이제 둘 다 항상 있다
    p["bitrate"] = p["max_bitrate"] = ""
```

기본값을 채운 뒤(`p`)를 보고 판정하고 있었다. 채우기 전에는 "타깃이 crf 만
말했다" 를 뜻했는데, 채운 뒤에는 영영 참이 될 수 없다. **잡이 무엇을
말했는지(`t`)로** 보도록 고쳤다. 테스트가 잡았다.

## 버린 선택

**잡 페이로드에 전부 적기.** 저쪽 `build_jobs` 가 `batch_size=32, imgsz=1280` 을
적어 보내면 된다. 그런데 그건 **우리 GPU 튜닝값을 저쪽 DB 코드가 알고 있어야
한다**는 뜻이다. GPU 를 바꾸면 저쪽을 고쳐야 한다.

**시그니처 기본값을 32/1280 으로 바꾸기.** 한 줄이면 되는데, `core` 는 노트북에서
CLI 로도 쓰는 계층이다. 거기 기본을 GPU 서버 기준으로 올리면 메모리 없는 곳에서
터진다. **계층마다 안전한 기본값이 다르다** — 그래서 채우는 자리가 따로 있어야 한다.

## 검증

테스트 셋.

| 무엇을 지키는가 |
|---|
| 잡이 말하지 않은 항목이 시그니처 기본값(1/960)이 아니라 튜닝값(32/1280)으로 채워진다 |
| **웹 화면과 큐 워커의 기본값이 키마다 같다** — 어긋나면 그 자리에서 실패한다 |
| `height: null`(스케일 생략)과 말 안 함(720p)이 여전히 구분된다 |

세 번째가 중요하다. 기본값을 채우는 변경은 "말 안 함" 의 의미를 바꾸는 일이라,
의도적으로 `null` 을 보내는 저쪽 규약과 충돌하기 쉽다.

**재측정이 남았다.** 이 문서의 숫자(49.5초·GPU 31%)는 고치기 **전** 값이고,
게다가 **개발기(L40S 45GB) 숫자**다. 운영 인스턴스는 더 작아질 예정이라 이 값을
그대로 저쪽에 넘기면 안 된다 — 운영 기종이 정해지면 거기서 다시 재야 한다.

## 덧 — 기본값을 올렸더니 작은 인스턴스가 위험해졌다

`batch_size=32` 는 45GB 짜리 개발기 기준이다. 운영에서 T4(16GB)나 L4(24GB)로
내려가면 32/1280 은 CUDA OOM 이 날 수 있고, **OOM 은 파이프라인 예외라 '영구
실패' 로 분류된다.** 인스턴스를 줄이는 순간 들어오는 영상이 전부 재시도 없이
실패한다 — 기본값을 올린 것이 그 지뢰를 심는 일이 될 뻔했다.

메모리 부족은 이 영상의 문제가 아니라 **환경의 문제**다. 그래서 잡 러너가 실패로
던지기 전에 배치를 절반씩 줄여 가며 다시 해 본다(32 → 16 → 8 → …). 1까지 내려도
안 되면 그때는 **일시** 실패다 — 더 큰 워커에서는 될 수 있기 때문이다.

줄여서 처리했으면 `notices` 에 `batch-reduced` 를 남긴다. 조용히 줄이면 "왜 이
인스턴스에서만 느리지" 가 원인 불명으로 남는다.

이건 튜닝을 대신하는 장치가 아니다. 줄여서 돌면 그만큼 느리므로, 운영 기종이
정해지면 `FA_BATCH_SIZE` 를 그 기종에 맞게 정해야 한다. 자동 축소는 **잘못 잡았을
때 죽지 않게** 하는 안전망이다.

## 배운 것

**진입점을 새로 만들 때 위험한 것은 로직이 아니라 기본값이다.** 로직이 틀리면
결과가 이상해서 바로 보이는데, 기본값이 다르면 **양쪽 다 정상으로 보이면서 다른
일을 한다.** 여기서는 성능으로 드러났지만(49.5초), `imgsz` 차이는 검출률로
드러났을 것이고 그건 훨씬 늦게 발견된다.

**"안전한 기본값" 은 계층마다 다르다.** `batch_size=1` 은 라이브러리로서는 옳고
GPU 서버로서는 틀렸다. 같은 값을 두 계층이 공유하려 하면 한쪽이 반드시 손해를
본다 — 채우는 자리를 따로 두는 게 답이다.

**측정이 도구의 판정보다 낫다.** 스모크 도구는 "검출이 가장 큰 단계" 라는 이유로
"진짜 GPU 한계입니다" 라고 출력했다. 30% 짜리를 병목이라 부른 것이다. 숫자를
그대로 봤기 때문에 오판을 잡았고, 도구도 같이 고쳤다(40% 미만이면 단일 병목이
없다고 말한다).
