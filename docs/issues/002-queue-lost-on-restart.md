# 002 · 재시작하면 대기 중인 작업이 전부 실패로 바뀐다

**상태** 해결됨

**한 줄** 서버를 내렸다 올리면 아직 시작도 안 한 대기 작업까지 `failed` 로
표시된다. 500건을 넣어두고 코드를 배포하면 남은 게 전부 날아간다.

## 증상

작업 500건을 큐에 넣고, 코드를 고쳐 서버를 재시작한다. 올라오고 나면 처리 중이던
1건뿐 아니라 **대기 중이던 499건도 전부 `failed`** 다.

```
서버 재시작으로 중단됨
처리 중 프로세스가 종료됐다
```

## 재현

```bash
# 1) 여러 건 제출
curl -s -X POST localhost:8000/api/jobs \
  -H 'Content-Type: application/json' -d '{"s3_prefix":"v1/input/kbs/"}'

# 2) 첫 건이 도는 동안 서버 Ctrl+C 후 다시 기동

# 3) 상태 확인 — 대기였던 것들도 failed 다
curl -s 'localhost:8000/api/jobs?limit=500' \
  | python3 -c 'import sys,json;from collections import Counter;print(Counter(j["status"] for j in json.load(sys.stdin)))'
```

## 원인

`service/jobs.py` 의 `recover_orphans()` 가 두 상태를 같이 처리한다.

```python
for j in all_jobs():
    if live or j.status not in ("queued", "running"):
        continue
    j.status = "failed"          # queued 도 여기로 온다
```

의도는 옳다. 프로세스가 죽으면 `running` 상태 파일이 그대로 남고, 그대로 두면
클라이언트가 영원히 "처리 중" 을 폴링한다. 그래서 기동 시 한 번 훑어 정리한다.

**놓친 것은 `queued` 와 `running` 의 성격이 다르다는 점이다.**

- `running` — 중간에 끊겼다. 결과물이 온전한지 알 수 없다. 실패로 두는 게 맞다.
- `queued` — **아직 아무 일도 일어나지 않았다.** 입력도 그대로고 부작용도 없다.
  다시 큐에 넣으면 그만이다.

기능을 만들 때는 "죽은 작업 = 실패" 로 한 덩어리로 봤고, 큐가 길어지는 사용
방식(폴더 통째 제출, 대기열 상한 없음)은 그 뒤에 생겼다. 두 변화가 만나는
지점을 다시 보지 않았다.

## 영향

**배포할 때마다 겪는다.** 그리고 큐가 길수록 손해가 크다 — 큐가 길다는 건 대량
처리 중이라는 뜻이므로, 하필 제일 아까울 때 날아간다.

복구도 수동이다. 실패 목록에서 키를 뽑아 다시 제출해야 하는데, 화면에는 일괄
재처리 버튼이 없다. `처리된 건 건너뛰기` 를 켜고 폴더를 다시 제출하면 되긴 하지만
**이미 처리된 건을 건너뛰는 것과 실패한 건만 다시 넣는 것은 다르다** — 후자를
바로 하는 길이 없다.

한 가지 다행인 것은 데이터가 깨지지는 않는다는 점이다. 결과물은 S3 에 없고 입력은
그대로이므로, 다시 돌리면 정상적으로 처리된다. 잃는 것은 시간과 사람의 손이다.

## 해결

**`queued` 는 다시 큐에 넣고, `running` 만 실패로 둔다.**

```python
# service/jobs.py — recover_orphans()
if j.status == "running":
    j.status = "failed"          # 중간에 끊겼다. 결과를 믿을 수 없다
elif j.status == "queued":
    j.stage, j.done, j.total = "", 0, 0
    JOBS[j.id] = j               # 아직 아무 일도 안 일어났다. 그대로 다시
    resume.append(j)
```

### 시도 횟수는 올리지 않는다

재큐할 때 `attempts` 를 그대로 둔다. **재시작은 그 작업이 실패한 것이 아니다.**
여기서 세면 배포를 세 번 하는 것만으로 재시도가 소진된다.

무한 재큐가 될 여지는 없다. 크래시 루프가 나더라도 **그 순간 돌던 작업은
`running` 이라 실패로 떨어지기 때문**이다. 매번 다른 작업이 하나씩 소모되므로
결국 끝난다.

### 제출은 워커가 한다

`jobs` 가 워커를 임포트하면 의존이 순환한다(`worker → jobs` 가 이미 있다).
그래서 `recover_orphans()` 는 **상태만 정리하고 재큐 대상을 돌려주고**,
`worker.resume_orphans()` 가 실제로 제출한다. 순서는 만들어진 순 그대로다 —
재시작했다고 순번이 뒤바뀌면 진행 상황이 안 읽힌다.

### 여러 프로세스는 껐다

`--workers N` 으로 띄우면 각 프로세스가 같은 작업을 재큐해 중복 처리한다.
`FA_RECOVER=0` 으로 끌 수 있게 하고, **한 프로세스만 켜 두라고 문서에 적었다.**

## 버린 선택

**프로세스별 소유권(claim)을 구현하기.** `job.json` 에 owner pid 를 적고 살아
있는지 확인하는 방식. 다중 프로세스에서 정확히 동작하지만, 지금 이 서비스는
단일 프로세스로 돌고 GPU 도 한 장이다. **분산 클레임 프로토콜을 그것 때문에
짓는 것은 비용이 값을 넘는다.** 환경 변수 하나와 문서 한 줄로 같은 사고를 막을
수 있으면 그쪽이 낫다.

**`running` 도 재큐하기.** 사실 안전하다 — 결과 키가 입력 키의 순수 함수라
덮어쓰고, 부분 결과물이 버킷에 올라가는 경로도 없다. 그런데도 실패로 두는
이유는 **"중단됐다" 는 사실이 기록에서 사라지지 않게 하려는 것**이다. 조용히
다시 도는 것과, 왜 다시 돌았는지 남는 것은 운영에서 전혀 다르다.

**재큐 횟수에 상한 걸기.** 위에서 본 대로 무한 루프가 성립하지 않아 필요 없다.
필드를 하나 늘리고 조건을 하나 더 만드는 값이 없다.

## 검증

테스트 네 개. 각각 되돌려 깨지는 것을 확인했다.

| 무엇을 지키는가 |
|---|
| 대기 중이던 작업은 재큐되고, 수행 중이던 것만 실패가 된다 |
| 재큐 순서가 만들어진 순서 그대로다 |
| **재큐가 재시도 횟수를 쓰지 않는다** |
| `FA_RECOVER=0` 이면 아무것도 건드리지 않는다 |
| 상태만 되돌리지 않고 실제로 워커에 제출한다 |

마지막 항목이 중요하다. 상태를 `queued` 로 돌려놓고 제출을 잊으면 **영원히
대기 상태로 남는다.** 화면에는 정상으로 보이므로 알아채기까지 오래 걸린다.

## 배운 것

**한 덩어리로 보이던 것이 사실은 둘이었다.** "죽은 작업" 이라는 이름 하나로
묶어 두었기 때문에 `queued` 와 `running` 의 차이가 안 보였다. 기능을 만들 때는
큐가 짧았고(단건 위주), 폴더 통째 제출과 무제한 대기열은 그 뒤에 생겼다.
**기존 코드가 새 사용 방식과 만나는 지점을 다시 보지 않은 것**이 원인이다.

**"안전하다" 와 "그렇게 해야 한다" 는 다르다.** `running` 재큐는 기술적으로
안전했지만, 그러면 중단됐다는 사실이 사라진다. 안전성만 보고 결정하면 운영에
필요한 정보를 잃는다.
