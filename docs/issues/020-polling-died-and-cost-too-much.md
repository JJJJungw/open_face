# 020 — 폴링이 한 번 실패하면 영원히 멈췄고, 도는 동안에는 너무 비쌌다

화면은 0.7초마다 서버에 "지금 어떤 상태냐" 를 묻는다. 그 루프에 문제가 둘 있었다.
하나는 **멈추는 것**이고 하나는 **비싼 것**이다.

## ① 요청 한 번 실패하면 다시는 안 묻는다

다음 회차 예약이 함수 **맨 끝**에 있었다.

```js
async function poll() {
  const [jobs, st] = await Promise.all([...]);
  if (asked !== filter || askedPage !== page) return;   // ← 나가는 길 1
  ...
  if (!jobs) return;                                    // ← 나가는 길 2
  ...
  if (page > lastPage) return goPage(lastPage);         // ← 나가는 길 3
  ...
  timer = setTimeout(poll, busy ? 700 : 5000);          // ← 여기까지 와야 예약된다
}
```

`fetch(...).catch(() => null)` 이므로 **서버 재시작이나 순간적인 네트워크 끊김이
곧바로 `jobs === null`** 이 된다. 그러면 두 번째 길로 나가고, 다음 회차는 걸리지
않는다. 화면이 그 시점에 얼어붙고 **서버가 돌아와도 새로고침 전까지 죽어 있다.**
진행률도, 건수도, 목록도 정지한다.

배포는 일상적인 조작이다. 900건을 돌려 놓고 화면을 띄워 둔 채 서버를 한 번
올렸다 내리면 그때부터 화면이 거짓말을 한다 — 그리고 그게 **멈췄다는 표시조차
없이** 마지막 상태 그대로 보인다.

재미있는 건 바로 아래 `safeCard` 에 이런 주석이 있었다는 것이다.

> 카드 한 장이 던져도 목록 전체가 사라지면 안 된다. 더 나쁜 것은 그 예외가
> `poll()` 을 뚫고 나가 **폴링이 멈추는** 것이다 — 화면이 그 시점에 얼어붙는다.

**같은 사고를 이미 알고 있었고 예외 경로만 막아 두었다.** 조기 `return` 은 결과가
같은데 안 막혀 있었다.

## ② 5건을 그리려고 900개를 읽는다

한 틱은 `/api/jobs` 와 `/api/status` 를 부른다. 실측:

```
작업 수     /api/jobs    /api/status
    0건        1.7 ms       1.4 ms
  100건        6.5 ms       1.3 ms
  900건       47.2 ms       2.1 ms
 3000건      169.1 ms       1.5 ms
```

`/api/status` 는 메모리만 봐서 평평하다. 비용은 전부 `/api/jobs` 다 — `all_jobs()`
가 매번 작업 폴더를 나열하고 `job.json` 을 **전부** 읽는다. 화면에 그리는 것은
5건인데.

0.7초 주기면 900건에서 코어의 **6.7%** 를 계속 먹는다. 그리고 그 CPU 는 지금
프레임을 렌더하고 있는 워커와 **GIL 을 나눠 쓴다.** 탭을 두 개 열면 두 배,
3000건이면 탭 하나에 24% 다.

## 한 일

**예약을 `finally` 로 옮겼다.** 어느 길로 나가든, 그리다가 예외가 나도 다음
회차가 걸린다. 화면이 한 번 잘못 그려지는 것과 영원히 멈추는 것은 다른 일이다.

다만 나가는 길 셋 중 둘은 **다른 폴링 체인에 넘기고** 나가는 것이라(탭이 바뀐
경우, 빈 쪽에서 물러나는 경우) 거기서 또 예약하면 체인이 둘이 되어 요청이 두 배로
나간다. `handedOff` 로 구분한다.

**실패하면 간격을 늘린다.** 서버가 죽어 있는 동안 초당 세 번씩 두드릴 이유가 없다.

```
정상 · 큐 돌 때   700ms      연속 실패 1회   1s
정상 · 유휴         5s       연속 실패 3회   4s
탭 숨김            15s       연속 실패 6회  30s (상한)
```

30초에서 멈추는 이유는, 서버가 돌아왔을 때 화면이 그 안에는 살아나야 사람이
"멈췄다" 고 읽지 않기 때문이다.

**안 보이는 탭은 묻지 않는다.** 운영자는 탭을 켜 둔 채 다른 일을 한다. 다시
보이는 순간에는 기다리지 않고 바로 한 번 묻는다 — 돌아왔는데 옛 화면이 15초 동안
남아 있으면 그것도 멈춘 것으로 보인다.

**끝난 작업은 다시 읽지 않는다.** `all_jobs()` 가 디스크 부분만 캐시한다(기본 5초,
`FA_LIST_CACHE_SEC`). 메모리에 있는 것은 **캐시하지 않는다** — 지금 돌고 있는
작업의 진행률은 매번 최신이어야 한다. 캐시하는 것은 끝났거나 실패했거나 취소된
것들이고, 그건 우리가 지우기 전까지 안 바뀐다.

```
900건 — 캐시 미스 50.2 ms (5초에 한 번)   적중 1.9 ms (나머지 전부)
0.7초 주기 CPU 점유:  6.7%  →  1.3%
```

**이게 안전한 이유는 작업 폴더의 주인이 하나이기 때문이다**(017). 다른 프로세스가
몰래 작업을 만들어 넣을 수 없으므로 우리가 모르는 변화는 없다. 017 을 못 박아 둔
것이 여기서 값을 한다 — 그게 없으면 이 캐시는 틀린 목록을 줄 수 있다.

캐시는 **폴더 경로를 같이 들고 있는다.** 운영에서는 안 바뀌지만 테스트는 매번
바꾸고, 그때 옛 작업이 새 폴더의 목록에 섞여 들어온다. 실제로 그렇게 네 개가
깨져서 알았다.

## 남은 것

**현황 화면은 10초마다 네 요청을 더 던진다.** 그중 `/api/s3/progress` 는
결과 프리픽스를 통째로 나열한다 — 결과물이 늘수록 비싸진다. 이건 별개 항목이라
손대지 않았다.

**목록 정렬은 여전히 매번 전체를 훑는다.** 캐시 적중 1.9 ms 의 대부분이 그것이다.
3000건에서 3.5 ms 이므로 지금 규모에서는 문제가 아니지만, 한 자릿수 더 커지면
정렬된 색인을 들고 있어야 한다.
