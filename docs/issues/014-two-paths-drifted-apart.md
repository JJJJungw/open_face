# 014 — 같은 일을 두 곳에서 하다가 여섯 군데가 갈라졌다

코드를 훑다가 나온 것들이다. **죽은 코드보다 중복이 문제였고**, 그중 몇 개는
이미 갈라져서 지금 틀린 값을 보여주고 있었다. 여기 적은 여섯 개는 전부 "지금
실제로 틀린 것"이고, 안 쓰는 코드 걷어내기는 따로 한다.

공통 원인이 하나다. **API 경로와 MSA 경로는 구조가 달라도 되지만 기록의 뜻은
같아야 한다.** 구조를 나눈 것은 의도였는데, 나누면서 "같아야 하는 것"에 이름만
같고 내용이 다른 값이 생겼다.

---

## ① 검수 필요가 CSV 에 영영 안 찍혔다

API 경로의 `job.finished` 에 `review_needed` 필드가 아예 없었다
(`service/worker.py`). MSA 경로는 넣고 있었다(`msa/journal.py`).

CSV 의 "검수 필요" 칸(`server.py:EXPORT_COLUMNS`)과 로그 한 줄 요약의
"⚠ 검수 필요"(`events.describe`)가 그 필드를 본다. **그래서 우리가 매일 쓰는
API 모드에서는 검수로 넘어간 영상도 그 칸이 항상 비어 있었다.** 별도로
`job.review` 줄을 하나 더 찍긴 하지만 CSV 는 줄 단위라 그걸로는 안 메워진다.

기록만 놓고 "이 폴더에서 검수로 빠진 게 몇 건인가" 를 셀 수 없었다는 뜻이다.
소급이 안 되는 종류의 손실이다.

## ② `소요(초)` 가 두 경로에서 다른 것을 쟀다

API 는 파이프라인 시간(`res.timing.total`), MSA 는 내려받기·올리기·재시도까지
포함한 벽시계(`elapsed_s`). 같은 칸에 나란히 찍히니 섞어서 비교하면 그냥 틀린
결론이 나온다.

**`seconds` 를 벽시계로 통일하고 `pipeline_s` 를 따로 뒀다.** 처리량을 셀 때
필요한 것은 벽시계이고("한 시간에 몇 편"), 병목을 볼 때 필요한 것은 파이프라인
시간이다. 둘 다 남기되 이름을 다르게 한다. CSV 에도 "처리(초)" 칸이 생겼다.

옛 저널 줄은 옛 뜻 그대로다 — 소급해서 고칠 방법이 없다.

## ③ 같은 OOM 이 한쪽에서만 회복됐다

메모리 부족은 **이 영상의 문제가 아니라 환경의 문제**라, MSA 경로는 배치를
절반씩 낮춰 가며 다시 해 본다(`job_runner.run_target`). API 경로는 그 회복이
없어서 그냥 실패했다. **두 경로가 같은 GPU 를 쓰는데 대응이 달랐다.**

판정도 두 벌이었다. `job_runner.is_oom` 은 소문자로 비교하고
`errors.classify` 는 대소문자를 가려서, `CUDA error: out of memory` 가 한쪽
에서만 OOM 이었다. 같은 예외가 경로에 따라 다른 코드로 남으면 나중에 로그로
원인을 세는 일이 성립하지 않는다.

배치 반감 루프를 `process_with_oom_retry(anonymizer, src, out, params)` 로 떼어
양쪽이 같이 쓰고, `classify` 는 판정을 다시 쓰지 않고 `is_oom` 을 부른다.

**부수 효과 하나.** 이제 OOM 은 그 자리에서 회복하므로 작업 시도를 소모하지
않는다. `test_transient_failure_is_retried` 가 OOM 을 재시도 확인용으로 쓰고
있었는데, 그건 이제 다른 층을 보는 테스트라 일시 오류를 다른 것으로 바꿨다.

## ④ `FA_PRELOAD=off` 가 안 먹었다

켜짐/꺼짐 판정이 다섯 군데에 따로 있었고 목록이 서로 달랐다.

    params.py           0 false no off ""
    events.py           0 false no off
    msa/config.py       0 false no off
    service/config.py   0 false no          ← _bool_env
    service/config.py   0 false False       ← PRELOAD 만 따로, strip·lower 도 없음

그래서 `FA_PRELOAD=off` 와 `FA_PRELOAD=FALSE` 는 **꺼지지 않았다.** 나머지 넷은
정상이었다. 같은 뜻으로 쓴 두 값이 반대로 동작하는 종류의 어긋남은 "왜 설정이
안 먹지" 로만 드러나서 원인 찾기가 아주 어렵다. 하필 이 값이 어제 죽은 서버를
찾게 만든 그 값이다(013).

`env.flag()` 하나로 모았다.

## ⑤ 경고가 화면에 영문 원문으로 떴다

경고 문자열에는 수치가 붙는다 — `low-detection-rate: 0.50%`. 화면은 그 문자열을
**통째로** 사전에서 찾고 있어서, 수치가 안 붙는 `no-detections` 만 한글로 나오고
나머지는 영문 코드가 그대로 떴다.

코드만 떼어 내 찾고 수치는 괄호로 뒤에 붙인다. 사전에 빠져 있던 세 개도 채웠다.

## ⑥ "남은 시간" 이 같은 화면에서 두 가지로 계산됐다

현황 타일은 작업 기준(`job_eta`), 사이드바 HUD 는 단계 기준(`eta`)인데 이름표는
둘 다 `이 작업` 이었다. `progress.py` 를 만든 이유가 "자를 하나로 쓰자" 였는데
화면이 그걸 반만 쓰고 있었다. HUD 도 `job_eta` 를 쓰게 했다.

## 확인

테스트 넷을 새로 붙였다. 두 경로의 `job.finished` 가 같은 필드를 갖는지,
`review_needed` 가 CSV 칸까지 실제로 닿는지, 같은 OOM 메시지가 양쪽에서 같은
코드로 분류되는지, OOM 이 시도를 소모하지 않고 배치를 낮추는지(8 → 4 를 실제로
확인한다), 그리고 켜짐/꺼짐 단어 목록이 하나인지.

## 남은 것

같은 훑기에서 나온 나머지는 아직 안 건드렸다. 안 쓰는데 남아 있는 것들
(`s3.py` 의 옛 이름 넷, 지운 `/download` 의 흔적, `FA_MSA_CONCURRENCY` 처럼
아무 일도 안 하는 설정, 안 쓰는 임포트 아홉), 그리고 문서 정리(README 에 아직
살아 있는 `/download`, 코드가 읽는데 `.env.example` 에 없는 환경변수 여섯).

단계 이름 표(`progress.STAGE_LABEL` vs 화면의 `STAGE_TEXT`)도 문구가 갈라져
있는데, 화면이 서버가 준 `stage_label` 을 안 쓰고 자기 표를 들고 있는 구조라
고치려면 조금 더 손이 간다. 다음 차례다.
