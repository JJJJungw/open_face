# 018 — 납품 비트레이트 대역이 강제된 적이 없었다

"화질 떨어뜨리는 걸 막는 로직이 아직 살아 있나" 를 확인하다가 나왔다. 검출·렌더
경로는 멀쩡했다. **정작 납품 규격이 지켜지지 않고 있었다.**

## 실측

720p 합성 클립 네 개를 실제로 통과시켜 재 봤다.

```
720p 단순    입력 1280x720     95kbps → 출력 1280x720    342kbps   ← 대역 한참 아래
720p 복잡    입력 1280x720  86509kbps → 출력 1280x720   3591kbps   ← 대역 위
1080p 복잡   입력 1920x1080    ...    → 출력 1280x720   3688kbps   ← 대역 위
480p 복잡    입력  854x480     ...    → 출력  854x480   3915kbps   ← 대역 위
```

해상도는 정확했다. 1280x720 이 들어가면 1280x720 이 나오고, 1080p 는 720p 로
줄고, 480p 는 확대하지 않는다. **비트레이트만 양쪽으로 다 샜다.**

## 왜 샜나

설정은 `-b:v 3500k -maxrate 4000k -bufsize 8000k` 였다. 문제가 둘이다.

**`-b:v` 는 목표 평균이지 하한이 아니다.** 인코더는 단순한 장면에서 "이 정도면
충분하다" 고 판단해 얼마든지 적게 쓴다. 정지에 가까운 컷에서 14 kbps 까지
내려간다. 방송 자료에는 그런 컷이 흔하다 — 자막 화면, 정지 사진, 고정 카메라.

`-minrate` 를 걸면 될 것 같지만 **x264 는 그걸 무시한다.** 직접 확인했다.

```
설정                                         단순(정지)   보통      복잡(노이즈)
b3500 max4000 buf8000  (예전)                    14kbps   3489kbps   3227kbps
b3200 min3000 max3500 buf3500                    14kbps   3191kbps   3083kbps   ← minrate 무시
b3200 min3200 max3200 buf3200 (CBR)              14kbps   3300kbps   3088kbps   ← 그래도 무시
b3200 min/max/buf 3200 + nal-hrd=cbr           3173kbps   3301kbps   3278kbps   ← 여기서 선다
```

실제로 비트를 채우게 하려면 **HRD 스터핑**을 켜야 한다. x264 는 `nal-hrd=cbr`,
NVENC 는 `-rc cbr` 이다. 그때 비로소 정지 화면도 3173 kbps 로 나온다.

**그리고 상한도 새고 있었다.** `-maxrate` 는 비디오 스트림의 순간 최대인데,
납품 검수는 파일을 열어서 잰다. 거기엔 오디오와 컨테이너 오버헤드가 같이 들어간다.
스트림이 대역 안이어도 파일은 넘어갈 수 있다.

## 무엇을 고쳤나

**목표를 대역 한가운데(3200k)에 두고 CBR 로 못 박았다.** 위끝(3500k)을 목표로
잡으면 오디오를 더하는 순간 넘어간다. 가운데 두면 오디오(128k)와 오버헤드가
얹혀도 파일 전체가 대역 안에 남는다.

오디오 비트레이트도 고정했다. ffmpeg 이 알아서 고르게 두면 채널 수와 원본에 따라
값이 달라지고, 그러면 파일 전체가 대역 안인지를 미리 계산할 수 없다.

고친 뒤 같은 방식으로 다시 쟀다. 이번엔 오디오까지 붙여서.

```
720p 단순    → 1280x720   3266kbps   규격내
720p 복잡    → 1280x720   3331kbps   규격내
1080p 복잡   → 1280x720   3373kbps   규격내
480p 단순    →  854x480   3266kbps   규격내
```

**단순한 장면에 비트를 낭비하는 것은 의도한 대가다.** 납품 기준이 "이 대역 안"
이면 아껴서 미달하는 것이 곧 반려다. 용량을 줄이고 싶으면 대역을 재협상할 일이지
인코더가 알아서 아끼게 둘 일이 아니다.

## 강제하고도 잰다

`check_delivery_bitrate()` 가 결과물을 다시 재서 대역을 벗어나면
`bitrate-out-of-band` 경고를 남기고, 그게 검수 대기로 이어진다. 강제했는데 왜 또
재느냐면 — 인코더가 갈릴 수 있고(NVENC↔libx264), 누가 대역을 환경 변수로 바꿔 둘
수 있다. 그때 조용히 나가면 900건을 납품한 뒤 검수에서 알게 된다.

다만 **아주 짧은 결과물은 재지 않는다.** CBR 은 버퍼가 차야 목표에 붙는다.

```
0.7초  2743 kbps      2초  3050 kbps      5초  3142 kbps      15초  3183 kbps
```

이건 인코딩이 잘못된 게 아니라 이 길이에서는 잴 수 없는 것이다. 2초 미만은
건너뛰되 **로그에는 남긴다** — 조용히 건너뛰면 "검사했는데 통과" 와 구분이 안 된다.
납품 클립은 분 단위라 실물에서는 걸리지 않는다.

## 진짜 문제는 테스트가 없었다는 것

대역이 새는 걸 2주 동안 아무도 몰랐다. 테스트가 없어서가 아니다 — `parse_bitrate`
가 "3500k" 를 파싱하는지, `bitrate_cap` 산수가 맞는지는 보고 있었다.
**인코딩된 파일을 실제로 재는 테스트가 하나도 없었다.** 설정값이 명령줄에
실리는 것까지만 확인하고, 그 명령줄이 실제로 무엇을 만들어 내는지는 안 봤다.

그래서 이번에 넣은 것은 고침보다 이쪽이 중요하다.

- `test_delivered_file_lands_inside_the_band` — 3초짜리를 실제로 인코딩해서 잰다.
  예전 설정으로 되돌리면 **214 kbps** 로 떨어지며 실패한다.
- `test_rate_args_turns_on_stuffing_per_encoder` — 인코더별로 스터핑이 켜지는지.
- `test_out_of_band_output_asks_for_a_human` — 벗어나면 검수로 가는지.
- `test_a_clip_too_short_to_measure_is_not_flagged` — 짧은 클립 오탐 방지.

계약 숫자(3000/3200/3500)를 못 박는 자리는 `tests/test_env.py` **하나뿐**이다.
나머지는 `params.DEFAULTS` 를 본다. 세 군데에 리터럴로 흩어 두면 대역이 바뀔 때
두 곳만 고치고 한 곳을 놓친다.

## 곁가지로 잡힌 것 둘

**`file_bitrate` 가 길이를 비트레이트로 읽고 있었다.** ffprobe 는 요청한 순서가
아니라 자기 고정 순서로 찍는다 — `format=bit_rate,duration` 을 달라고 해도
`duration` 이 먼저 나온다. 값만 받아 자리로 세면 틀린다. 키를 남기고 이름으로
읽는다. (처음 짤 때 실제로 이렇게 틀렸고, 대역 검사가 `0k < 3000k` 를 뱉어서
드러났다.)

**`video_duration` 을 이름이 같은 함수로 덮어썼다.** 새 헬퍼를 추가했는데 이미
같은 이름이 있었고, 기존 것은 **비디오 스트림** 길이를 재는 물건이었다 —
컨테이너 길이를 쓰면 오디오가 영상보다 긴 파일에서 프레임 수를 과대추정해 정상
영상을 거부한다. 파이썬은 조용히 덮어쓴다.
`test_audio_longer_than_video_is_not_rejected` 가 잡았다. 그 테스트가 없었으면
"마이크가 늦게 끊긴 녹화물" 이 전부 실패로 떨어질 뻔했다.

## GPU 에서도 확인했다 — 그리고 더 나빴다

위의 실측은 전부 libx264 다. 운영 EC2 는 NVENC 를 쓰고 rate control 구현이
달라서, 같은 실험을 실제 장비(L40S)에서 다시 돌렸다. 30초짜리 단색 화면 —
인코더가 제일 아끼고 싶어 하는 입력이다.

```
vbr  (-rc vbr  -b:v 3500k -maxrate 4000k -bufsize 8000k)      27 kbps
cbr  (-rc vbr -rc cbr -b:v 3200k -maxrate 3200k -bufsize 3200k)   3203 kbps
```

**27 kbps.** libx264 에서 본 14 kbps 가 CPU 인코더 특유의 현상이 아니었다는
뜻이고, 더 중요하게는 **납품을 실제로 수행하는 장비에서 그러고 있었다**는
뜻이다. 정지에 가까운 컷 — 자막 화면, 정지 사진, 고정 카메라 — 은 규격 미달
정도가 아니라 사실상 화질이 없는 파일로 나가고 있었다.

`-rc vbr` 뒤에 `-rc cbr` 을 붙여 뒤엣것이 이기는 것도 같이 확인했다. 우리 코드가
후보 표의 옵션 뒤에 rate control 을 붙이는 구조라 그 순서에 기대고 있다.

재현은 이 한 줄이다.

```
ffmpeg -y -v error -f lavfi -i color=c=navy:s=1280x720:r=30:d=30 \
  -c:v h264_nvenc -preset p4 -rc vbr -b:v 3500k -maxrate 4000k -bufsize 8000k \
  -pix_fmt yuv420p /tmp/nv.mp4
ffprobe -v error -show_entries format=bit_rate -of default=nw=1 /tmp/nv.mp4
```

## 남은 것

**실제 방송 클립으로는 아직 안 쟀다.** 여기 숫자는 전부 합성 영상(단색·노이즈·
testsrc)이라 실물의 압축 특성과 다르다. 대역 안에 들어오는 것은 CBR 이 보장하지만,
그 대역에서 **화질이 납품 기준을 만족하는지**는 다른 질문이고 눈으로 봐야 한다.
