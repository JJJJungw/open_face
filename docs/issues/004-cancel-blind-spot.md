# 004 · S3 전송 중에는 취소가 먹지 않는다

**상태** 해결됨

**한 줄** 취소는 파이프라인의 진행률 콜백에서만 확인한다. 그 앞뒤인 S3
내려받기·올리기 구간에서는 취소를 눌러도 전송이 끝날 때까지 안 멈춘다.

## 증상

큰 파일을 내려받는 중에 취소를 누르면 화면은 취소된 것처럼 보이는데, 서버는
계속 받고 있다. 다 받은 뒤에야 실제로 멈춘다.

## 재현

```bash
# 큰 영상을 제출하고, 로그에 "S3 에서 내려받는다" 가 뜬 직후 취소
curl -s -X POST localhost:8000/api/jobs/$JID/cancel
# 서버 로그를 보면 다운로드가 계속 진행된다
```

## 원인

취소는 협조적(cooperative)으로 구현돼 있다. 플래그를 세우면 **작업 쪽이 스스로
확인해서 빠져나온다.** 확인하는 자리는 하나뿐이다.

```python
# service/worker.py — run() 안
def progress(stage, done, total):
    if j.cancel:
        raise JobCancelled()      # 여기서만 끊긴다
```

이 콜백은 파이프라인이 프레임마다 부른다. 프레임을 돌기 시작해야 불린다는 뜻이다.
그런데 `run()` 은 이 순서로 진행한다.

```
① S3 내려받기      ← 콜백 없음. 취소 안 됨
② 파이프라인       ← 콜백 있음. 취소 됨
③ S3 올리기        ← 콜백 없음. 취소 안 됨
```

강제로 죽이는 방법을 안 쓴 것은 의도였다. 스레드를 밖에서 죽이면 임시 파일과
GPU 락이 어중간하게 남는다. 협조적 취소를 고른 것은 맞는 판단이었는데,
**"협조할 지점" 을 한 군데만 만든 것**이 빠진 부분이다.

## 영향

크지 않다. 다만 두 가지가 걸린다.

**첫째, 화면이 거짓말을 한다.** 취소 요청은 `200` 을 돌려주고 상태도 바뀌지만
실제 작업은 계속 돈다. 사용자는 멈춘 줄 알고 다른 걸 시작한다.

**둘째, 잘못 넣은 대량 배치를 빨리 못 멈춘다.** 500건을 잘못된 파라미터로 넣었을
때 취소가 즉시 먹지 않으면 GPU 시간이 그만큼 더 나간다. 다만 대기 중인 건은
시작 전에 취소가 확인되므로(`run()` 초입), 실제로 손해 보는 건 지금 전송 중인
한 건뿐이다.

한 가지 짚어둘 것은 **전송 중 취소가 데이터를 깨뜨리지는 않는다**는 점이다.
다운로드는 임시 경로가 아니라 최종 입력 경로로 받지만, 중단되면 작업 자체가
취소 상태가 되고 그 디렉터리는 통째로 정리된다.

## 해결

**협조할 지점을 하나 더 만든다.** 구조를 바꾼 게 아니라 확인하는 자리를 늘렸다.

boto3 의 `download_file` · `upload_file` 은 `Callback` 을 받는다. 전송된
바이트마다 불리므로 거기서 같은 플래그를 본다.

```python
def cb(chunk):
    if j.cancel:
        raise s3mod.TransferAborted()
    seen[0] += chunk
    progress(stage, min(seen[0], total), total)
```

이제 확인 지점이 셋이다.

```
① S3 내려받기   ← 전송 콜백
② 파이프라인    ← 진행률 콜백
③ S3 올리기     ← 전송 콜백
```

### 취소는 S3 오류가 아니다

처음 구현에서 바로 걸렸다. 콜백에서 예외를 던졌더니 `download()` 의
`except Exception` 이 그것까지 잡아 **`S3Error` 로 감쌌다.** 사용자가 취소를
누른 것이 "S3 호출에 실패했습니다" 로 보고됐다. 원인이 완전히 뒤바뀐다.

저장소 계층에 신호를 하나 만들어 통과시킨다.

```python
class TransferAborted(Exception):
    """전송 콜백이 중단을 요청했다. S3 오류가 아니므로 감싸지 않는다."""
```

워커의 예외(`JobCancelled`)를 그대로 쓰지 않은 이유는 **의존 방향** 때문이다.
`storage` 가 `service` 를 임포트하면 화살표가 거꾸로 선다. 저장소가 아는
신호로 던지고, 워커가 받아서 자기 언어로 되돌린다.

### 덤으로 진행률이 붙었다

같은 콜백으로 전송 진행률까지 보고한다. 지금까지 큰 파일을 받는 동안에는
`준비 0%` 로 멈춘 것처럼 보였다. AV1 전사 단계에서 이미 같은 문제를 겪고 별도
단계로 만들어 해결했는데, **다운로드 구간은 그대로 남아 있었다.**

```
S3 내려받기 62% · 남은 시간 0:08
```

분모는 `head_object` 로 한 번 가져온다. 작업 하나에 한 번이라 왕복이 아깝지
않다 — 목록에서 크기를 들고 다니게 만드는 쪽이 더 번거롭다.

### 이중 확인

전송 계층이 콜백의 예외를 삼키는 경우를 대비해 전송 직후에도 한 번 더 본다.

```python
store.download(...)
if j.cancel:
    raise JobCancelled()
```

boto3 는 예외를 올려보내는 것으로 알고 있지만, **확인 비용이 한 줄이고 틀렸을
때의 대가는 "취소가 안 먹는다" 다.** 싼 쪽으로 둔다.

## 버린 선택

**스레드를 밖에서 죽이기.** 임시 파일과 GPU 락이 어중간하게 남는다. 애초에
협조적 취소를 고른 이유이고, 그 판단은 지금도 맞다.

**`JobCancelled` 를 storage 에서 임포트하기.** 한 줄이면 되지만 의존 방향이
거꾸로 선다. `core`·`storage` 는 `service` 를 몰라야 배치 워커로 떼어 쓸 수
있다.

**전송을 청크 단위로 직접 구현하기.** `get_object` 로 스트림을 받아 우리가
루프를 돌면 확인 지점을 마음대로 넣을 수 있다. 그런데 boto3 의 멀티파트·재시도·
스레드 최적화를 전부 잃는다. **콜백 하나로 되는 일에 전송기를 다시 짤 이유가
없다.**

## 검증

테스트 여섯 개. 각각 되돌려 깨지는 것을 확인했다.

| 무엇을 지키는가 |
|---|
| 내려받는 동안 진행률이 보고된다 (합이 파일 크기와 같다) |
| 올리는 동안도 마찬가지다 |
| 콜백이 중단을 요청하면 전송이 그 자리에서 멈춘다 |
| **중단이 `S3Error` 로 감싸지지 않는다** |
| 중단된 전송이 `failed` 가 아니라 `cancelled` 로 끝난다 |
| 취소 플래그가 서면 워커의 콜백이 실제로 중단을 요청한다 |
| `size_of()` 가 진행률의 분모를 준다 (몰라도 전송은 된다) |

## 배운 것

**"협조적 취소" 를 고른 것은 맞았는데, 협조할 지점을 하나만 만들었다.** 설계
방식을 정하고 나면 그 방식이 필요한 자리를 **전부** 찾아야 한다. 진행률 콜백은
파이프라인 안에만 있었고, 그 앞뒤에 다른 긴 작업(전송)이 있다는 것을 그때는
보지 않았다.

**예외를 감쌀 때는 무엇을 감싸면 안 되는지도 정해야 한다.** `except Exception`
으로 전부 잡아 `S3Error` 로 바꾸는 코드는 "S3 호출에서 나는 예외" 를 감쌀
생각이었지, "우리가 그 안에서 일부러 던진 신호" 까지 감쌀 생각은 아니었다.
넓은 `except` 는 나중에 들어올 것까지 삼킨다.

**같은 증상을 두 번 겪었다.** 전사 구간이 `준비 0%` 로 보이던 문제를 이미
고쳤는데, 다운로드 구간은 그대로 뒀다. **한 곳을 고칠 때 "같은 모양이 다른
데도 있나" 를 묻지 않으면 반드시 다시 만난다.**
