# 022 — 끝나는 길이 넷인데 정리는 둘에만 있었다

작업이 끝나는 길은 넷이다. 업로드 성공, 실패, 취소, 그리고 **서버 재시작으로
중단됨**. `drop_media()`(작업 폴더에서 영상만 지우고 `job.json` 은 남긴다)는
앞의 둘에만 있었다.

```
worker.py:266   실패          → drop_media  ✓
worker.py:477   업로드 성공    → drop_media  ✓
worker.py:493   취소          →  없음
jobs.py:496     재시작 중단    →  없음
```

## 왜 영구히 남나

빠진 둘이 하필 **TTL 정리 대상이 아닌 상태**로 끝난다.

```python
ttl = (config.FAILED_TTL if j.status in ("failed", "cancelled") else config.JOB_TTL)
if not ttl:
    continue          # FA_FAILED_TTL_MIN 기본값이 0 이다
```

`failed` 와 `cancelled` 를 안 지우는 것은 의도한 것이다 — 배치로 수백 건을 돌린
뒤 몇 건이 실패했을 때 입력과 사유가 남아 있어야 원인을 본다. 그런데 그 정책이
"영상까지 들고 있는다" 는 뜻은 아니었다. 원인을 보는 데 필요한 것은
`job.json` 이고, 원본은 버킷에 그대로 있다.

측정했다. 가짜 버킷에 7.6MB 짜리를 넣고 처리 중에 취소했다.

```
버킷의 원본:            7627 KB
취소 뒤 서버 디스크:    input.mp4  7627 KB   ← 100%
```

## 규모는 생각보다 작다

처음에는 "`cancel-all` 한 번에 수십 GB" 로 봤는데 그건 틀렸다. **워커는 한 번에
한 편만 돌린다.** 900건을 `cancel-all` 해도 대기 중이던 것들은 아직 내려받지
않았으므로 남는 것은 그때 돌던 한 편뿐이다.

그래서 실제 규모는 **취소 한 번에 원본 하나, 재시작 한 번에 원본 하나**다. 방송
클립이 200~400MB 이므로 납품 기간 동안 취소·배포를 스무 번쯤 하면 4~8GB 다.
당장 터지지는 않지만 회수되지 않는 종류이고, 여유가 `FA_MIN_FREE_MB`(2GB) 밑으로
내려가면 **새 작업이 507 로 거절되기 시작한다.**

## 재시작 쪽에는 하나가 더 있었다

중단된 작업을 `failed` 로 표시하면서 **저널에 아무것도 안 남겼다.** 저널은
`job.started` 만 들고 있고 끝나는 이벤트가 없다. 그러면 시간 축으로 읽는 쪽에는
그 작업이 **영원히 돌고 있는 것**으로 보인다. 저널이 존재하는 이유가 바로 그
축인데(`events.py` 첫머리: "01:04 에 시작해서 01:05 에 한 번 실패하고 01:06 에
다시 시작했다 같은 시간 축은 job.json 에 남지 않는다") 정작 그 축이 끊겨 있었다.

다른 종료 경로는 전부 이벤트를 낸다 — `job.finished`, `job.failed`,
`job.cancelled`, `job.review`. 재시작 복구만 조용했다.

## 한 일

취소 경로와 재시작 복구에 `drop_media()` 를 넣고, 중단된 작업에
`job.failed`(`code="interrupted"`)를 낸다.

`jobs.py` 가 `events` 를 임포트하게 됐는데 순환은 없다 — `events` 는 `env` 와
`timefmt` 만 본다.

## 배운 것

**종료 경로가 늘어날 때 정리가 따라오지 않았다.** 취소(007)와 재시작 복구(002)는
각각 다른 시점에 들어왔고, 그때마다 "상태를 어떻게 남길까" 는 생각했지만 "그
작업이 들고 있던 것을 어떻게 치울까" 는 안 봤다. 원래 있던 두 경로에는 정리가
있었으므로 **패턴이 이미 있었는데 새 경로가 그걸 안 따라간 것**이다.

이런 건 종류별로 한 번에 훑어야 잡힌다. `drop_media` 를 부르는 곳을 세어 보는
데 1분이 걸렸는데, 그 1분을 아무도 안 썼다.
