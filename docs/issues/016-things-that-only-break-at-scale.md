# 016 — 900건을 돌려야 드러나는 것들

훑기 네 번째. 이번에는 **동시성과 실패 경로**만 봤다. 죽은 코드나 중복이 아니라,
"한 건으로 테스트하면 절대 안 나오는데 900건을 돌리면 나오는 것" 이다.

여섯 개를 고쳤고 네 개는 판단이 필요해 남겼다.

---

## ① 재시작이 대기 중인 작업을 영원히 잠재웠다 — 제일 나쁜 것

재시도·보류 대기는 **프로세스 안의 타이머**가 재운다(`worker.schedule`). 그
타이머는 재시작하면 사라진다. 그래도 유실되지 않는다고 믿었던 이유는 그 작업이
`queued` 로 남아 있어 기동 때 다시 큐에 들어가기 때문이다 — 실제로
`schedule()` 의 주석이 그렇게 적혀 있다.

그런데 나중에 들어온 가드가 그 전제를 깼다.

```python
# worker.run() 초입
if j.not_before and time.time() < j.not_before:
    return          # ← 아무것도 다시 걸지 않고 물러난다
```

`recover_orphans` 는 `queued` 를 다시 큐에 넣으면서 `stage/done/total/overall`
은 지웠지만 **`not_before` 는 그대로 뒀다.** 그래서

    재시작 → 다시 큐에 넣음 → run() 이 "아직 때가 아니다" 로 물러남 → 끝

이 작업을 다시 넣어 줄 곳은 어디에도 없다(`enqueue`·`schedule`·`resume_orphans`
셋뿐이고 셋 다 안 부른다). **영원히 `queued`** 로 남아 대기 수를 부풀리고,
뒤에 선 작업들의 예상 대기 시간을 계속 늘린다.

한 건짜리 사고가 아니다. S3 가 잠깐 흔들리면 워커가 초당 한 건씩 실패시키므로
수백 건이 동시에 `waiting="retry"` 가 되고, **그걸 보고 서버를 다시 띄우는 것이
운영자가 할 법한 바로 그 행동**이다. 그 순간 수백 건이 전부 잠든다.

`recover_orphans` 가 `not_before` 와 `waiting` 을 같이 지운다.

## ② 처리 도중에 저장소가 바뀌면 A 에서 받아 B 에 올렸다

`worker.run()` 이 내려받을 때와 올릴 때 각각 `get_store()` 를 불렀다. 그 사이에
누가 화면에서 저장소를 바꾸면 — 지금은 화면에서 바꿀 수 있다(011) — 이 영상은
한 곳에서 받아서 **다른 곳에 올라간다.** 오류 하나 없이 조용히.

비식별화한 결과물이 엉뚱한 버킷에 떨어지는 것은 이 서비스에서 제일 나쁜
결말이다. 그 사이에 연결을 끊었다면 `get_store()` 가 `None` 이라 올리는 자리에서
`AttributeError` 가 나는데, 그건 '알 수 없는 오류' 로 분류돼 **GPU 파이프라인을
네 번 더 돌린다.**

두 군데를 고쳤다. 작업 하나는 처음부터 끝까지 **같은 스토어 객체**를 쓴다. 그리고
`POST /api/storage` 에도 해제(`DELETE`)와 같은 "돌고 있으면 거절" 가드를 붙였다 —
해제만 막고 변경을 열어 두면 같은 사고를 다른 문으로 낼 수 있다.

## ③ 업로드 직후의 취소가 결과물을 미아로 만들었다

```python
store.upload(res.output, key, ...)
if j.cancel:
    raise JobCancelled()        # ← 여기서 끝나면
with jobs.LOCK:
    j.s3_output = key           # ← 이게 안 찍힌다
```

결과물은 버킷에 있는데 그걸 가리키는 기록이 없다. 아무도 그 파일을 못 찾고,
`/result` 는 "결과물이 남아 있지 않습니다" 라고 한다. 더 나쁜 건 다시 제출할 때다
— `skip_processed` 가 결과 버킷을 대조하므로 **'이미 처리됨' 으로 거절된다.**
취소했다면서.

900건 배치를 중간에 멈추는 것(`cancel-all`)은 일상적인 조작이라 언제든 걸린다.
올린 다음에는 먼저 기록하고 취소를 본다.

## ④ 제출 요청이 이벤트 루프를 통째로 붙들고 있었다

`POST /api/jobs` 만 `async def` 였다(다른 라우트는 전부 `def` 라 스레드풀에서
돈다). 그 안에서 버킷 목록 조회 두 번과, 키마다 `makedirs` + `job.json` 쓰기 +
`_tracked.json` 읽고 쓰기가 돈다 — 900건이면 **`await` 한 번 없이 수천 번의
파일 작업**이다.

그동안 이벤트 루프는 다른 요청을 하나도 못 받는다. 폴더를 제출한 **바로 그
순간에** 화면이 얼어붙고, `/api/health` 도 안 답한다. 그게 준비 상태 검사라
오케스트레이터가 제출 도중에 컨테이너를 재시작할 수 있고 — 그러면 ①로 이어진다.

multipart 를 걷어내면서(015) `await request.json()` 이 유일한 await 였으므로,
평범한 `def` + `Body` 로 바꿨다. 이제 스레드풀에서 돈다.

## ⑤ 디스크가 차면 워커가 청소부가 됐다

디스크 여유가 모자라면 `run()` 이 정리를 한 번 강제로 돌린다. 그런데 900건이
이미 큐에 앉아 있으므로 **900번 연속으로** 돈다 — 첫 번째 말고는 회수할 것이
없는데도. 한 번 훑는 데 작업 폴더 나열과 `job.json` 900개 읽기가 들어간다.
워커는 그동안 일을 하나도 못 하고, 목록·지표 API 도 같은 파일들을 두고 경합한다.

정리에 최소 간격(`FA_SWEEP_MIN_GAP`, 기본 20초)을 뒀다. 백그라운드 스레드는
자기 주기가 있으므로 `force=True` 로 항상 돈다.

## ⑥ 진척률 폴더 목록이 워커의 락을 900번 뺏었다

`track_prefix` 가 전역 `JOBS` 락을 **파일 읽기·쓰기 내내** 붙들고 있었다. 그
락은 워커가 프레임마다 잡고 폴링이 한 번에 여섯 번씩 잡는다. 폴더 목록은 작업
상태와 아무 상관이 없는데도, 900건 제출이 렌더링 중인 작업의 진행률을 900번
멈춰 세웠다. 자기 잠금으로 옮겼다.

## 남긴 것 — 판단이 필요하다

**재시도 예산이 벽시계다.** `RETRY_DELAYS=5,30,60` 이라 한 작업의 네 번 시도가
**95초 안에** 다 끝난다. S3 가 10분 끊기면, 그 사이에 첫 시도를 한 작업은 전부
네 번을 소진하고 영구 실패로 떨어진다 — 건강한 1분을 만나 볼 기회도 없이. 수백
건을 손으로 다시 제출해야 한다. 디스크 부족은 이 문제를 알고 있어서 시도를 안
쓰는 보류로 처리하는데(`defer`), 상류 장애는 그 대접을 못 받는다. 고치려면
"상류가 통째로 죽은 것" 과 "이 파일이 문제인 것" 을 구분해야 해서 정책 결정이
필요하다.

**`--workers N` 은 지금 안전하지 않다.** README 는 지원한다고 적혀 있고 GPU 락도
프로세스 간으로 만들어 뒀는데, 정리 스레드가 다른 프로세스의 작업 폴더를 지울 수
있고(메모리만 보고 판단한다), `/cancel` 은 다른 프로세스가 든 작업에 대해
**조용히 아무 일도 안 하면서 200 을 준다**, 그리고 복구가 모든 프로세스에서
동시에 돌아 같은 작업을 중복 처리한다. 셋 다 실재한다. 단일 프로세스로 못 박고
문서를 고칠지, 제대로 지원할지를 정해야 한다.

**하드 킬이 입력 파일을 흘린다.** boto3 는 `input.mp4.<난수>` 로 받다가 이름을
바꾸는데, 그 사이에 프로세스가 죽으면 그 임시 파일이 남는다. 정리는 `.anon-` 으로
시작하는 것만 지우고, 실패 보관은 기본이 무기한이라 영원히 남는다. 며칠짜리 배치가
쌓이면 ⑤로 이어진다.

**결과 서명 주소가 한 시간이다.** 인증이 붙어도 이미 나간 주소는 그동안 아무나
연다. 몇 분으로 줄이는 것이 맞다고 보는데, 화면 동작을 한 번 확인하고 정하는
편이 낫다.
