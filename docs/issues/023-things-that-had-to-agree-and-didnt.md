# 023 — 같아야 하는 것들이 또 갈라져 있었다

자격 증명 쪽을 손대기 전에 바닥을 봤다. 교착·강결합·의존 구조를 훑었는데,
**교착은 없었고**(그건 아래) 대신 "두 곳에 적힌 같은 사실" 이 세 쌍 갈라져
있었다. 셋 다 지금 **틀린 값을 보여주고 있었다.**

009·013·014 가 전부 같은 형태였다. 그때마다 고쳤는데 또 나왔다.

## ① `/api/metrics` 가 검수 대기를 통째로 빠뜨렸다

`jobs.STATUSES` 는 여섯인데 `metrics.queue_metrics` 는 다섯을 **손으로 다시
적어** 두었다 — `review` 가 없다.

```python
by = {k: [...] for k in ("queued", "running", "done", "failed", "cancelled")}
```

그래서 검출 0건으로 검수에 걸린 영상은 `done` 에도 안 들어가고 어느 통에도 안
담긴다. 결과적으로 **처리량(`throughput_1h`)·평균 처리시간·최장 처리시간에서
통째로 사라진다.**

더 나쁜 것은 `jobs.recent_stats()` 는 `done`+`review` 를 같이 센다는 점이다.
**같은 화면의 두 평균이 서로 다른 모집단을 쓰고 있었다.** 어느 쪽이 맞는지는
숫자만 봐서는 알 수 없다.

이제 `jobsmod.STATUSES` 를 그대로 쓰고, "처리가 끝난 것" 에 `review` 를 포함한다
— 검수 대기도 **처리는 끝났다.** 남은 것은 사람의 확인이다.

## ② GPU 메모리 부족이 "알 수 없는 오류" 로 나갔다

`job_runner` 가 던지는 stage 는 여덟인데 문구 표(`STAGE_FACE`)에는 일곱만
있었다. 빠진 것이 `oom` 이다.

```python
raise JobError(..., stage="oom")        # :338
STAGE_FACE = { payload, download, weights, model, process, stall, upload, unknown }
```

없으면 `unknown` 으로 떨어져 저쪽 화면에 **"알 수 없는 오류입니다 / 잠시 뒤
자동으로 다시 시도합니다"** 가 간다. 같은 상황을 API 경로는 정확히 말한다 —
"GPU 메모리가 부족합니다 / batch_size 나 imgsz 를 낮추면 통과할 수 있습니다".

**014 가 고쳤다고 적은 바로 그 문제(같은 OOM 이 경로마다 다르게 보임)가 판정이
아니라 문구 층에서 재발했다.** `is_oom` 통일과 `process_with_oom_retry` 공유는
됐는데 표만 안 따라왔다.

## ③ 모든 실패가 "영구" 로 기록됐다

저널 문장 생성기는 이 필드 하나만 본다.

```python
bits.append("일시적" if row.get("transient") else "영구")     # events.py:342
```

MSA 경로는 `transient` 를 싣고 **API 경로는 안 실었다.** 그래서 재시도를 세 번
다 쓰고 죽은 일시적 오류도 로그 화면과 CSV 에서 "영구" 다. 운영자가 "이건 다시
넣으면 되는 건가" 를 판단하는 근거가 그 한 단어인데.

덤으로 `events.LIST_FIELDS` 와 CSV 열에 **`code` 가 없었다.** 사유는 `detail`
산문에만 있어서, 목록과 CSV 만으로는 "무엇 때문에 몇 건 실패했나" 를 셀 수 없다.
`code`·`policy` 를 목록에 넣고 CSV 에 "오류 코드"·"재시도" 칸을 만들었다.

## 교착은 없다

같이 확인한 것이라 여기 적어 둔다. 잠금은 아홉이다(`jobs.LOCK`, `_TRACK_LOCK`,
`_sweep_lock`, `_disk_cache_lock`, `_anon_lock`, `events._lock`, `_LOAD_LOCK`,
저널 락, flock 둘).

- **잠금 중첩이 한 군데도 없다.** AST 로 전수 확인했다. 잠금 순서 역전이
  성립할 구조 자체가 없다.
- 함수 호출을 타고 다시 잡는 경로는 하나뿐인데(`gpu_lock` → `get_anonymizer`
  의 `_anon_lock`) **다른 종류의 잠금이고 순서가 한 방향**이다. 반대로 잡는 곳이
  없어 역전이 안 된다.
- 잠금을 쥔 채 하는 I/O 는 전부 작다 — `job.json` 한 개 쓰기, 빈 폴더 지우기,
  저널 한 줄 append, 64줄짜리 `_tracked.json`. **네트워크나 큰 파일을 잠금
  안에서 만지는 곳은 없다.**

## 안 고치고 남긴 것

**`storage/` 가 `service/errors` 를 임포트한다**(`base.py:93`, `s3.py:59`).
지연 임포트로 순환은 피했지만, 그 결과 **MSA 워커 컨테이너에서 S3 오류가 나면
`fastapi` 를 임포트하려 든다** — `worker.txt` 에 fastapi 가 없으므로 그 자리에서
ImportError 다. `job_runner.py:159` 는 "fastapi 를 끌고 오기 때문" 이라며 이걸
명시적으로 피했는데 `storage` 는 안 지켰다. 고치려면 문제 코드 상수를 fastapi 를
안 끄는 곳으로 내려야 해서 범위가 커진다.

**확장자 목록이 세 벌이었다** — `config.py`, `metrics.py`, 오류 문구. 앞의 둘은
이번에 합쳤다(`metrics` 가 `config.VIDEO_EXT` 를 임포트). 문구는 남았다.

**상태 하나를 추가하려면 파일 6개 25곳을 고쳐야 한다.** 상태가 이름 목록이
아니라 전이 규칙·TTL 정책·집계 분류·정렬 순위·화면 라벨 다섯 개가 각기 다른
파일에 흩어진 개념이라서다. ①이 그 증거다.

## 곁가지 — 흔들리던 테스트가 잘못된 자를 쓰고 있었다

전체 실행의 25% 쯤에서 `test_batch_size_does_not_change_result` 가 실패했다.
그 테스트는 배치 1 과 6 의 결과물을 **최대 픽셀 차이**로 비교하면서, 독스트링에
"인코딩 잡음은 한 자릿수라 진짜 차이와 안 섞인다" 고 적어 뒀다.

재 보니 사실이 아니었다. **같은 배치끼리 비교해도** 최대값이 0~46 사이에서
튄다.

```
같은 배치 1v1   최대  10 · 8 · 0      평균절대차 0.005 · 0.003 · 0.000
다른 배치 1v6   최대  37 · 37 · 8     평균절대차 0.008 · 0.010 · 0.003
```

즉 46 은 배치 크기와 무관하고, 결과물이 손실 압축을 거치는 데다 인코딩이
실행마다 비트 단위로 같지 않아서 경계 픽셀 하나가 그만큼 흔들리는 것이다.
**테스트가 주장하는 것과 실제로 재는 것이 달랐다.**

평균절대차로 바꿨다. 잡음은 0.01 아래에 머물고, 자가 실제로 듣는지도 확인했다 —
박스를 15px 밀면 2.276(최대 203)이 나온다. 임계값 0.5 는 잡음의 50배, 진짜
차이의 4.5분의 1 자리다.

**임계값만 올려서 통과시키지 않은 이유**가 있다. 46 을 넘기려면 60쯤으로
올려야 하는데, 그 테스트가 잡겠다던 "진짜 차이" 도 그 근처에서 시작한다.
그러면 통과하는 테스트가 아무것도 안 지킨다.

여기서도 처음 만든 검증 스크립트가 틀렸다. `FakeDetector` 를 상속해 박스를
미는 흉내를 냈는데 메서드 이름(`detect_batch`)을 잘못 써서 아무것도 안 바뀌었고,
"자가 안 듣는다" 는 결론이 나왔다. **검증 도구가 틀렸을 가능성을 먼저 의심해야
했다** — 잡음과 정확히 같은 값(0.007)이 나온 것이 그 신호였다.

## 배운 것

**"단일 출처" 는 값을 한 곳에 두는 것이 아니라 다른 곳에서 그걸 쓰게 만드는
것이다.** `jobs.STATUSES` 는 이미 있었다. `metrics` 가 안 썼을 뿐이다.

그래서 이번 테스트는 값을 비교하지 않고 **소스에 단일 출처를 참조하는지**를
본다(`"jobsmod.STATUSES" in src`). 값만 비교하면 두 벌을 다 고쳐 통과시킬 수
있고, 그러면 다음에 또 갈라진다.
