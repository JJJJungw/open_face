# 005 · 진척률 API 가 폴더 수만큼 S3 를 호출한다

**상태** 미해결

**한 줄** `GET /api/s3/progress` 는 폴더마다 목록 호출을 한 번씩 한다. 현황
화면이 10초마다 부르므로, 폴더가 늘면 왕복도 그만큼 늘고 캐시가 없다.

## 증상

지금 규모(폴더 3개)에서는 체감되지 않는다. 코드를 읽다 발견했다.

## 재현

```bash
time curl -s 'localhost:8000/api/s3/progress' > /dev/null
```

폴더를 늘려 가며 재면 호출 시간이 폴더 수에 비례해 는다.

## 원인

`service/metrics.py` 의 `folder_progress()` 구조다.

```python
done_keys = store.processed_keys()        # 1회 (30초 캐시 있음)
folders, objects = store.list(root)       # 1회
for f in folders:
    keys = [... for o in store.list(f)[1] ...]   # 폴더마다 1회 — 캐시 없음
```

결과물 쪽은 왕복을 줄이려고 **한 번만 나열하고 대조**하도록 신경 써서 짰다
(객체마다 HEAD 를 날리면 수백 번 왕복한다). 그런데 **입력 쪽은 폴더마다 부른다.**
같은 함수 안에서 한쪽만 최적화한 셈이다.

`processed_keys()` 에는 30초 캐시가 있지만 `list()` 에는 없다. 그리고 현황 화면은
10초마다 `loadOverview()` 를 부른다.

## 영향

폴더 N개면 요청당 **N+1 회** 왕복이다.

| 폴더 수 | 요청당 호출 | 화면을 1시간 켜둘 때 |
|---|---|---|
| 3 | 4 | 1,440 회 |
| 20 | 21 | 7,560 회 |
| 100 | 101 | 36,360 회 |

S3 `LIST` 요청 비용 자체는 크지 않다. 실제로 걸리는 건 **지연**이다. 폴더가 20개면
현황 화면 한 번 갱신에 21번의 왕복이 직렬로 쌓이고, 그동안 워커 스레드가 아니라
FastAPI 이벤트 루프 쪽이 막힌다.

**입력 폴더 목록은 거의 안 변한다.** 하루에 몇 번 바뀔 데이터를 10초마다 새로
읽고 있다는 게 문제의 본질이다.

## 고려한 방향 (아직 결정 전)

가장 단순한 것은 `list()` 에도 짧은 캐시를 두는 것이다. 다만 파일 브라우저는
`list()` 를 쓰면서 **새로고침 버튼을 누르면 즉시 반영되기를 기대한다.** 캐시를
그 경로까지 걸면 버튼이 거짓말을 한다. 캐시를 붙일 자리는 `list()` 가 아니라
`folder_progress()` 여야 한다.

두 번째 방향은 접근 자체를 바꾸는 것이다. 입력을 `list_all(root)` 로 **한 번에**
받아 폴더별로 나누면 왕복이 폴더 수와 무관하게 2회(입력 1 + 결과 1)로 고정된다.
페이지네이션이 늘어나지만 왕복 수는 객체 수/1000 에만 비례한다. 폴더가 많을수록
이쪽이 유리하고, 코드도 더 짧아진다.

지금 규모에서는 어느 쪽이든 체감이 없다. 다만 **폴더가 늘어나는 방향으로 쓸
서비스**라는 점이 분명하므로(방송사별·날짜별로 나뉠 것이다) 미리 정리해 두는 게
맞다고 본다.
