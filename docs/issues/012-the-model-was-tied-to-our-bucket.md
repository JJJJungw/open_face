# 012 — 저장소는 고를 수 있게 해 놓고 모델은 우리 버킷에 묶여 있었다

## 어떻게 드러났나

011 에서 첫 실행 관문을 만들었다. 남이 클론해 와서 자기 버킷을 고르고 통과하는
그림이다. 그런데 그 사람이 통과한 다음 첫 영상을 넣으면 이렇게 된다.

```
가중치가 없고(weights/yolo-facev2.pt) ... s3://그사람버킷/v1/model/yolo-facev2.pt
```

`FA_WEIGHTS_SOURCE` 의 기본값이 `s3` 였고, 그건 **우리 버킷을 전제한 값**이다.
남의 버킷에 우리 가중치가 있을 리가 없다. 저장소를 고를 수 있게 만들어 놓고
모델을 우리 것에 묶어 두면 앞의 노력이 통째로 무의미하다 — 관문은 통과시키고
그다음에 멎는데, 심지어 900건을 넣은 뒤에 멎을 수도 있다.

재미있는 건 `scripts/setup_weights.py` 에는 이미 공개 릴리스 폴백이 있었다는 것이다.
**준비 스크립트만 알고 런타임은 몰랐다.** 스크립트를 돌리는 사람은 우리뿐이라
그동안 아무도 안 밟았다.

## 한 일

기본을 `auto` 로 바꿨다. 순서는 셋이다.

1. 이미 있으면 그대로 — 네트워크 호출조차 없다
2. 버킷에 있으면 거기서
3. 없으면 업스트림(clibdev/YOLO-FaceV2) 공개 릴리스에서

우리 EC2 는 1 이나 2 에서 끝나므로 **동작이 예전과 같다.** 남의 환경은 3 으로
산다. 버킷을 먼저 보는 이유는 원래 근거 그대로다 — 배포마다 GitHub 릴리스에
의존하면 레이트 리밋에 걸리고, 네트워크 정책에 막히고, 업스트림 태그가 바뀌면
어제와 다른 파일을 받는다.

**넘어갈 때 왜 넘어갔는지 남긴다.** 조용히 넘어가면 우리 버킷 설정이 잘못된
날에도 그냥 GitHub 에서 받아 와서, 한참 뒤에 "왜 매번 40MB 를 받지" 로
나타난다. 셋 다 실패하면 세 갈래를 전부 적어서 던진다 — 하나만 알려 주면
사람이 그것만 붙들게 된다.

**화면이 미리 말한다.** 관문에 "모델 가중치 — 아직 없습니다. 처음 처리할 때
자동으로 내려받습니다 (약 40MB)" 와 받아 올 주소가 같이 뜬다. 40MB 를 받는
일이 첫 영상에서 갑자기 일어나면 사람은 그걸 고장으로 읽는다.

## 왜 저장소에 안 넣나

두 가지다. 40MB 이진 파일이라 git 이 감당할 물건이 아니고, 애초에 **우리가
만든 것이 아니다.** 업스트림(GPL-3.0)이 배포하는 릴리스 자산을 그대로 가리키는
편이 사본을 떠서 다시 배포하는 것보다 출처가 분명하다. 사내망처럼 거기 못 닿는
환경은 `FA_WEIGHTS_URL` 로 자기 미러를 넣으면 된다.

## 테스트가 바깥으로 나가고 있었다

기본을 바꾸자마자 `test_without_s3_...` 가 **통과하는데 실패했다** — 예외를 안
던진 것이다. 폴백이 실제로 GitHub 에서 40MB 를 받아 왔기 때문이다. 테스트가
인터넷에 의존하면 비행기에서도 CI 에서도 못 돈다. `transfer.fetch` 를 막는
autouse 픽스처를 두고, 넘어가는 동작은 가짜 fetch 로 따로 본다.

## 남은 것

`third_party/YOLO-FaceV2` 리포는 여전히 `scripts/setup_weights.py` 가 클론한다.
체크포인트를 언피클하려면 그 코드가 있어야 해서 가중치만으로는 안 된다.
런타임이 이것까지 알아서 하게 할지는 아직 안 정했다 — 서버가 기동 중에 git
clone 을 하는 것은 그것대로 놀랍다.
