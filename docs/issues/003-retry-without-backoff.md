# 003 · 재시도에 간격이 없어 3회가 순식간에 소진된다

**상태** 미해결

**한 줄** 일시적 오류로 판단해 재시도하지만 즉시 다시 던진다. S3 가 몇 초
흔들리면 3회가 밀리초 안에 끝나고 실패로 떨어진다.

## 증상

리전을 일부러 틀리게 준 서버로 재시도 경로를 확인할 때 드러났다. `attempts` 가
1 → 2 → 3 으로 오르는 것을 보려고 2초 간격으로 폴링했는데, **첫 조회에 이미
`failed 3` 이었다.**

```
failed 3 s3_upstream
failed 3 s3_upstream
...
```

## 재현

```bash
# 죽은 엔드포인트를 물린 서버를 8001 에 띄우고
AWS_ENDPOINT_URL_S3=http://127.0.0.1:9 .venv/bin/uvicorn \
  face_anonymizer.service.server:app --port 8001

# 작업 하나 제출하면 즉시 failed 3 이 된다
```

## 원인

`service/worker.py` 의 `fail_or_retry()` 가 상태만 되돌리고 곧바로 다시 제출한다.

```python
if retryable:
    j.status, j.done, j.total, j.stage = "queued", 0, 0, ""
    ...
    EXEC.submit(run, j.id)      # 간격이 없다
```

재시도라는 개념을 넣을 때 **"몇 번"만 정하고 "언제"를 정하지 않았다.** 횟수는
설정으로 열어 뒀는데(`FA_MAX_ATTEMPTS`) 간격은 아예 개념이 없다.

## 영향

**재시도가 사실상 아무것도 막지 못한다.** 재시도가 존재하는 이유는 "잠깐 흔들리는
것" 을 넘기기 위해서인데, 세 번이 같은 순간에 일어나면 그 잠깐을 하나도 못 넘긴다.
실제로 막을 수 있는 건 "정확히 그 밀리초에만 실패하는 오류" 뿐이고, 그런 건 거의
없다.

현실적인 시나리오는 이렇다. S3 가 5초간 502 를 준다. 그 사이 큐에 있던 작업이
차례로 3회씩 소진되며 전부 `failed` 로 떨어진다. **S3 가 정상으로 돌아온 뒤에도
자동으로 회복되지 않는다.** 사람이 실패 목록을 보고 다시 넣어야 한다.

여기에 002(재시작 시 큐 손실)와 겹치면 더 나쁘다. 대량 배치 도중 S3 가 잠깐
흔들리면 수십 건이 한꺼번에 죽고, 그걸 되살릴 일괄 재처리 수단도 없다.

## 고려한 방향 (아직 결정 전)

**지수 백오프**가 표준이다. 1회 실패 뒤 2초, 2회 뒤 8초 정도.

다만 워커가 하나뿐이라 구현이 단순하지 않다. `EXEC` 에 `sleep` 을 넣으면 그동안
**뒤에 쌓인 정상 작업까지 멈춘다.** 재시도 대기가 큐 전체를 막는 것은 원래
문제보다 나쁘다.

그래서 "언제 다시 시도할지" 를 작업에 적어 두고, 워커가 꺼낼 때 아직 이르면
건너뛰는 방식이 맞아 보인다. 작업 상태에 `retry_after` 같은 필드가 하나 늘고,
큐를 꺼내는 규칙이 "가장 오래 기다린 것" 에서 "지금 실행 가능한 것 중 가장 오래
기다린 것" 으로 바뀐다.

**지터(jitter)** 도 같이 봐야 한다. 여러 건이 같은 오류로 동시에 실패하면 백오프
시각도 같아져서, 회복 순간에 한꺼번에 몰린다. 간격에 임의성을 조금 섞는다.
