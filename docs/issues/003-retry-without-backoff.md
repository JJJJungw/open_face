# 003 · 재시도에 간격이 없어 3회가 순식간에 소진된다

**상태** 해결됨

**한 줄** 일시적 오류로 판단해 재시도하지만 즉시 다시 던진다. S3 가 몇 초
흔들리면 3회가 밀리초 안에 끝나고 실패로 떨어진다.

## 증상

리전을 일부러 틀리게 준 서버로 재시도 경로를 확인할 때 드러났다. `attempts` 가
1 → 2 → 3 으로 오르는 것을 보려고 2초 간격으로 폴링했는데, **첫 조회에 이미
`failed 3` 이었다.**

```
failed 3 s3_upstream
failed 3 s3_upstream
...
```

## 재현

```bash
# 죽은 엔드포인트를 물린 서버를 8001 에 띄우고
AWS_ENDPOINT_URL_S3=http://127.0.0.1:9 .venv/bin/uvicorn \
  face_anonymizer.service.server:app --port 8001

# 작업 하나 제출하면 즉시 failed 3 이 된다
```

## 원인

`service/worker.py` 의 `fail_or_retry()` 가 상태만 되돌리고 곧바로 다시 제출한다.

```python
if retryable:
    j.status, j.done, j.total, j.stage = "queued", 0, 0, ""
    ...
    EXEC.submit(run, j.id)      # 간격이 없다
```

재시도라는 개념을 넣을 때 **"몇 번"만 정하고 "언제"를 정하지 않았다.** 횟수는
설정으로 열어 뒀는데(`FA_MAX_ATTEMPTS`) 간격은 아예 개념이 없다.

## 영향

**재시도가 사실상 아무것도 막지 못한다.** 재시도가 존재하는 이유는 "잠깐 흔들리는
것" 을 넘기기 위해서인데, 세 번이 같은 순간에 일어나면 그 잠깐을 하나도 못 넘긴다.
실제로 막을 수 있는 건 "정확히 그 밀리초에만 실패하는 오류" 뿐이고, 그런 건 거의
없다.

현실적인 시나리오는 이렇다. S3 가 5초간 502 를 준다. 그 사이 큐에 있던 작업이
차례로 3회씩 소진되며 전부 `failed` 로 떨어진다. **S3 가 정상으로 돌아온 뒤에도
자동으로 회복되지 않는다.** 사람이 실패 목록을 보고 다시 넣어야 한다.

여기에 002(재시작 시 큐 손실)와 겹치면 더 나쁘다. 대량 배치 도중 S3 가 잠깐
흔들리면 수십 건이 한꺼번에 죽고, 그걸 되살릴 일괄 재처리 수단도 없다.

## 해결

### 간격을 목록으로 정한다 — 5초 · 30초 · 60초

| 시도 | 언제 | 누적 |
|---|---|---|
| 1회 | 즉시 | — |
| 2회 | 실패 후 **5초** | 5초 |
| 3회 | 실패 후 **30초** | 35초 |
| 4회 | 실패 후 **60초** | **95초** |

처음 1회 + 재시도 3회로 **95초짜리 창**을 덮는다.

**공식(base × factor^n) 대신 목록으로 뒀다.** 처음에는 5초에 4배씩(5·20)으로
짰는데, 읽어서 바로 와닿지 않는다는 지적을 받고 바꿨다. 지수가 이론적으로 좋은
이유는 자릿수를 넘나드는 장애를 적은 시도로 덮으려는 것인데, **재시도가 서너
번뿐이면 그 이점이 거의 없다.** `5,30,60` 은 보는 순간 동작이 보인다.

첫 간격이 5초인 것은 **흔한 경우를 빨리 통과시키기 위해서**다. S3 순단은
대부분 여기서 끝난다.

창이 95초로 긴 것은 **거의 순수한 이득**이다. 대기가 큐를 막지 않으므로(아래
예약 방식) 처리량 손해가 없고, 그 시간을 쓰는 것은 정말 일시적일 수 있는
오류뿐이다 — 권한 없음이나 키 오타는 애초에 재시도 대상이 아니라 즉시 실패한다.
**오래 기다리는 경우는 기다릴 가치가 있는 경우다.**

지터는 ±20%. 여러 건이 같은 순간에 실패했을 때 회복하는 순간 한꺼번에 몰리지
않게 흩뜨린다. **지금은 워커가 하나라 효과가 크지 않다** — 어차피 직렬화된다.
그래도 넣은 것은 워커가 늘거나 배치 실행기로 갈 때 필요해지고, 비용이 한 줄이기
때문이다.

시도가 목록보다 많으면 마지막 값을 계속 쓴다. `FA_MAX_ATTEMPTS` 를 올려도
계산이 깨지지 않는다.

### 자는 게 아니라 예약한다

```python
def schedule(jid, delay):
    t = threading.Timer(delay, lambda: EXEC.submit(run, jid))
    t.daemon = True
    t.start()
```

워커가 하나뿐이라 `sleep` 을 넣으면 **뒤에 쌓인 정상 작업까지 그동안 멈춘다.**
재시도 대기가 큐 전체를 막는 것은 원래 문제보다 나쁘다. 작업에 `not_before` 를
적어 두고 그 시각에 다시 제출한다. 그동안 상태는 `queued` 라 큐는 계속 돈다.

타이머는 프로세스가 죽으면 사라진다. 그래도 유실되지 않는데, 그 작업이 `queued`
로 남아 있어 **재시작 때 다시 큐에 들어가기** 때문이다. [002](002-queue-lost-on-restart.md)
를 먼저 고쳐 둔 것이 여기서 값을 했다.

### 재시도와 보류를 나눈다

성격이 다르다.

| | 재시도 | 보류 |
|---|---|---|
| 무엇 | 실패했다 | **아직 시작할 조건이 안 됐다** |
| 언제 | S3 오류, GPU 메모리, 내부 오류 | 디스크 부족 |
| 간격 | 5초 → 20초 (지수) | 60초 고정 |
| 시도 횟수 | 쓴다 | **안 쓴다** |
| 끝 | 3회 소진 시 `failed` | 30분 넘으면 `failed` |

디스크 부족은 이 작업이 실패한 것이 아니다. 세 번 확인했다고 포기할 일이 아니라
**여유가 생길 때까지 기다리면 되는 일**이다. 그래서 시도 횟수를 쓰지 않는다.

대신 상한을 뒀다. 영구히 찬 디스크를 영원히 숨기면 안 된다. 30분이면 사람이
알아챌 시간은 되고, 그 뒤에는 명확한 사유로 실패한다.

이 구분 때문에 `run()` 의 순서도 바뀌었다. **조건 확인이 시도 횟수를 올리기
전으로** 왔다. 뒤에 있으면 보류할 때마다 재시도가 하나씩 소모된다.

### 화면이 이유를 말한다

`not_before` 가 미래인 `queued` 는 그냥 "대기" 가 아니다.

```
재시도 대기 · 0:18 뒤 · 재시도 1/3
보류 · 1:00 뒤
디스크 여유 공간이 부족합니다
```

안 그러면 큐에 있는데 왜 안 도는지 알 수 없다.

## 버린 선택

**고정 간격 하나.** 장애가 얼마나 갈지 모르는데 숫자 하나로 맞출 수 없다.
짧게 잡으면 못 넘기고 길게 잡으면 짧은 장애에 낭비한다.

**지수 공식.** 처음에는 이렇게 짰다(5초, 4배). 틀린 것은 아니지만 재시도가
서너 번뿐인 상황에서는 **읽기 어려운 대가만 남는다.** 목록이 더 정확하고 더
읽기 쉽다.

**횟수만 늘리기.** 100번을 즉시 시도해도 5초짜리 장애는 못 넘긴다. CPU 만
태운다. 필요한 것은 횟수가 아니라 간격이었다.

**`time.sleep()`.** 워커가 하나라 큐 전체가 멈춘다.

**재시도를 아예 없애기.** `처리된 건 건너뛰기` 가 있어서 폴더를 다시 제출하는
비용이 거의 없다. 나름 합리적인 선택지였지만, **사람이 알아채야 한다**는 것이
걸렸다. 밤새 500건을 돌려놓고 아침에 실패 50건을 발견해 다시 넣는 것과, 그 50건이
알아서 회복돼 있는 것은 다르다.

**보류에 상한을 안 두기.** 영구히 찬 디스크가 조용히 숨는다. 대기 중이라는
표시는 실패보다 눈에 덜 띈다.

## 검증

테스트 여섯 개. 각각 되돌려 깨지는 것을 확인했다.

| 무엇을 지키는가 |
|---|
| 간격이 설정한 목록(5·30·60)을 따르고 합이 95초다 |
| 시도가 목록보다 많아도 계산이 깨지지 않는다 |
| 간격에 지터가 있다 (전부 같으면 몰린다) |
| **자지 않고 예약한다** — 큐가 멈추지 않는다 |
| 재시도 대기 중인 작업이 화면에 이유와 남은 시간을 준다 |
| **보류는 시도 횟수를 쓰지 않는다** |
| 보류가 상한을 넘으면 실패로 남는다 |
| 실제로 시작하면 대기 표시가 지워진다 |

테스트가 5초씩 기다리지 않도록 재시도 테스트는 간격을 0.01초로 낮췄고, 간격
계산 자체는 별도 테스트로 검증한다. **테스트를 빠르게 하려고 검증을 빼면 안
된다** — 나눠서 둘 다 지킨다.

## 배운 것

**"몇 번" 만 정하고 "언제" 를 안 정했다.** 재시도라는 개념을 넣을 때 횟수는
설정으로 열어 뒀는데 간격은 아예 개념이 없었다. 기능에 이름을 붙이면 다 만든
것처럼 느껴지는데, 그 기능이 실제로 값을 내는 조건이 무엇인지는 따로 물어야
한다. 여기서는 **"재시도가 값을 내려면 그 사이에 세상이 바뀌어야 한다"** 였다.

**공식이 항상 목록보다 나은 것은 아니다.** 지수 백오프는 교과서에 있는 답이라
자연스럽게 그걸 골랐는데, 우리 조건(재시도 서너 번, 워커 하나)에서는 그 이점이
거의 사라진다. 남는 것은 읽기 어려움뿐이었다. **정석을 고를 때도 그 정석이 왜
정석인지, 그 이유가 우리 상황에 성립하는지 확인해야 한다.**

**한 문제를 고치니 다른 문제의 해법이 생겼다.** 001 에서 디스크 부족을 실패로
처리할 수밖에 없었던 이유는 "미룬다" 를 표현할 수단이 없어서였다. `not_before`
가 생기자 그대로 풀렸다. **비슷한 형태의 문제가 둘 이상 보이면 각각 때우기 전에
공통 구조를 먼저 찾는 편이 낫다.**
