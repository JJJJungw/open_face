# 006 · 목록이 100건에서 잘려 화면 전체가 "유휴" 로 보인다

**상태** 해결됨

**한 줄** 작업 목록은 **최신순 100건**만 돌려주는데 워커는 **오래된 것부터**
처리한다. 창과 처리 순서가 반대라, 300건짜리 배치에서는 지금 돌고 있는 작업이
창 밖으로 밀려난다. 그리고 화면의 모든 숫자가 그 잘린 창에서 계산됐다.

## 증상

`kbs/` 폴더 297건을 제출한 직후 화면이다.

```
전체 남은 시간   계산 중        남은 작업 100건
수행중 · 대기    0 / 100        유휴
완료             0              기록 없음
처리 속도        — × 실시간
```

사이드바도 `전체 100 · 대기 100 · 수행중 (없음) · 완료 (없음)`. 목록 맨 위
카드는 `K_00299` 이고 `앞에 296건` 이라고 적혀 있다. **297건이 대기 중인데
목록은 100건이라 하고, 그 100건의 맨 위는 줄의 맨 뒤였다.**

같은 순간 `/api/metrics` 는 다르게 답했다.

```
대기 297건 · GPU 메모리 5.2/45 GB · 워커 NVIDIA L40S
```

즉 **서버는 멀쩡히 일하고 있었고, 화면만 그것을 못 보고 있었다.**

## 재현

작업을 101건 이상 넣으면 재현된다.

```bash
curl -s "localhost:8000/api/jobs" | python3 -c "
import sys, json
rows = json.load(sys.stdin)
print(len(rows), [r['status'] for r in rows[:3]])"
# 100 ['queued', 'queued', 'queued']   ← 수행중이 없다

curl -s localhost:8000/api/metrics | python3 -c "
import sys, json; m = json.load(sys.stdin); print(m['running'], m['depth'])"
# 1 296                                 ← 실제로는 돌고 있다
```

## 원인

두 가지가 겹쳤다. 하나만으로는 이렇게까지 안 됐다.

### 창의 방향이 처리 순서와 반대다

```python
# service/jobs.py
return sorted(merged.values(), key=lambda x: -x.created)   # 최신순

# service/server.py
return [jobs.snapshot(j, ...) for j in rows[:limit]]       # 앞에서 100건
```

워커는 만들어진 순서대로 꺼낸다(`EXEC` 는 `max_workers=1` 인 FIFO). 그러니까
**처리는 오래된 것부터, 목록은 최신 것부터** 다. 297건을 넣으면 목록에 잡히는
100건은 큐의 꼬리(`K_00200`~`K_00299`)이고, 지금 처리 중인 `K_00000` 근처는
197칸 뒤에 있어 잘려 나간다.

최신순 자체가 틀린 기본값은 아니다. 작업이 100건 이하일 때는 전부 보이니까
아무 문제가 없었고, 지금까지 테스트한 규모가 딱 그 정도였다.

### 화면의 모든 숫자를 그 창에서 셌다

```javascript
function kpis(jobs, st) {
  const running = jobs.find(j => j.status === 'running');   // 창 안에 없다
  const queued  = jobs.filter(j => j.status === 'queued');  // 창 크기가 상한
  const done    = jobs.filter(j => j.status === 'done');    // 항상 0
  ...
}
```

`navCounts` 도, `hud` 도, `avgSeconds` 도 같은 배열을 셌다. **목록을 자른 결정이
집계까지 같이 잘라 버렸다.** 표시 상한(`FA_LIST_LIMIT`)은 "화면에 몇 장의
카드를 그릴까" 를 정하는 값이지 "몇 건이 대기 중인가" 를 정하는 값이 아닌데,
코드에서는 그 둘이 같은 배열 하나였다.

`완료 0 · 기록 없음` 도 여기서 나온다. 평균 처리 시간은 창 안의 완료 카드에서
계산했는데 완료는 전부 창 밖이었다. `전체 남은 시간` 이 `계산 중` 에 멈춘 것도
마찬가지 — 한 건에 걸리는 시간을 알 방법이 창 안에 없었다.

## 영향

**대시보드가 100건을 넘는 순간 통째로 무의미해진다.** 그런데 이 서비스는
애초에 수백 건짜리 폴더를 통으로 넣으라고 만든 것이다. 즉 **가장 중요한
사용 시나리오에서만 고장 나는 화면**이었다.

숫자로 보면, 297건 배치에서 화면이 사실대로 말한 값은 하나도 없었다.

| 화면 | 실제 |
|---|---|
| 수행중 0 | 1 |
| 대기 100 | 296 |
| 완료 0 | (진행에 따라) |
| 남은 작업 100건 | 297건 |

실질적인 위험은 **오해가 행동으로 이어진다**는 것이다. "유휴" 로 보이면 서버가
멈춘 줄 알고 재시작하거나 같은 폴더를 다시 제출하게 된다. 재시작은 대기 큐를
다시 세우고(002 에서 고친 경로라 유실은 없지만 시간은 든다), 재제출은 GPU
시간을 그대로 두 배로 쓴다. 실제로 이 화면을 보고 가장 먼저 든 의심이
"워커가 죽었나" 였다.

## 해결

### 1. 세는 일과 보여 주는 일을 분리한다

집계는 목록과 **다른 경로**로 온다. 메모리(`JOBS`)만 보므로 0.7초 폴링에
얹어도 디스크를 훑지 않는다.

```python
# service/jobs.py
def counts():          # 상태별 건수 + total
def running_snapshot() # 지금 도는 한 건 (없으면 None)
def recent_stats()     # 최근 완료 5건의 평균 처리 시간·실시간 대비
```

셋 다 `GET /api/status` 에 실린다. 화면은 이미 매 폴링마다 이걸 부르고 있어서
왕복이 늘지 않는다.

```javascript
const running = st.running || jobs.find(j => j.status === 'running');
const queued  = c.queued || 0;
```

`st.running` 을 먼저 보는 게 핵심이다. **목록을 어떻게 자르든, 어떤 상태로
좁혀 보든, 돌고 있는 작업은 항상 보인다.**

### 2. 목록 정렬을 실행 순서로 바꾼다

```python
def list_key(j):
    rank = {"running": 0, "queued": 1}.get(j.status, 2)
    if rank == 2:
        return (rank, -(j.finished or j.created))   # 끝난 것은 최근 것부터
    return (rank, j.created)                        # 수행중·대기는 먼저 온 순
```

수행중이 맨 위, 그 다음이 **다음 차례**, 끝난 것은 뒤에 최근 순. 부수 효과로
대기 카드의 `앞에 N건` 이 위에서부터 `0, 1, 2…` 로 읽힌다. 전에는 맨 위가
`앞에 296건` 이라 그 숫자가 무슨 뜻인지 알아보기 어려웠다.

### 3. 상태 필터를 서버로 옮긴다

`poll()` 이 `?status=done` 을 붙여 부른다. 전에는 잘린 100건을 받아서 화면에서
걸렀기 때문에, 완료가 창 밖에 있으면 '완료' 탭이 비어 보였다.

### 4. 목록을 쪽으로 나누고, 기본 목록은 '아직 처리할 일' 로 좁힌다

처음에는 "상한을 100에서 500으로 올리고 넘치면 '더 보기'" 로 갔다. 리뷰에서
**"카드는 페이지네이션이 맞고, 완료된 건 사이드바 완료 쪽에만 있어야 한다"**
는 지적을 받고 바꿨다. 그 판단이 맞다. 아래에 왜 처음 판단이 틀렸는지 적는다.

```
GET /api/jobs?status=active&offset=200      # 3쪽
```

`status=active` 는 **수행중 + 대기**, 즉 아직 처리할 일이다. 이게 화면의 기본
목록이 됐다. 끝난 것은 '완료' 탭에, 실패는 '실패' 탭에, 전부 보고 싶으면
'전체 기록' 에 있다. 사이드바가 이제 여섯 줄이지만 **각 줄이 실제로 다른
목록**을 연다.

```
진행중  293      ← 기본
수행중    1
대기    292
완료      4
실패      —
전체 기록 297
```

그 아래에 쪽 막대를 둔다.

```
이전   1–100 / 293건 · 1 / 3 쪽   다음
```

한 쪽이 100건인 근거는 실측이다. 297건 큐를 헤드리스 브라우저에 그려 잰 값.

| 건수 | 서버 응답 | 크기 | 화면이 그리는 시간 | 폴링 예산(0.7초) 대비 |
|---|---|---|---|---|
| 100 | 14.9 ms | 27 KB | 9.5 ms | 1% |
| 300 | 14.0 ms | 82 KB | 24.6 ms | 4% |
| 1000 | 40.0 ms | 273 KB | 183.0 ms | 26% |
| 3000 | 154.2 ms | 822 KB | 524.6 ms | 75% |

**상한을 올리는 방식은 규모가 커지면 반드시 다시 터진다.** 500으로 올리면
297건 폴더는 편해지지만 3000건 폴더에서 0.7초마다 0.5초를 그리는 데 쓴다.
쪽으로 나누면 폴더가 몇천 건이어도 화면은 언제나 한 쪽 값(1%)만 낸다.

그리고 **완료를 기본 목록에서 뺀 것이 사실 더 큰 효과**다. 배치가 끝나 갈수록
목록의 대부분이 완료 기록이 되는데, 그때 정작 보고 싶은 건 남은 대기다.
끝난 것과 할 일을 한 줄에 섞으면 목록이 길어질수록 쓸모가 줄어든다.

### 덤으로 걸린 것 셋

고친 화면을 헤드리스 브라우저로 297건 상태에서 실제로 그려 보다가 나온 것들이다.
**셋 다 화면을 눈으로만 봤으면 못 찾았고, 숫자가 맞는지 확인하러 들어갔다가
걸렸다.**

**① 탭을 바꾸면 옛 응답이 새 화면을 덮어썼다.** '완료' 를 누르면 즉시 폴링이
나가는데, 그 직전에 나갔던 폴링(필터 없음)이 뒤늦게 도착해 방금 고른 탭 위에
전체 목록을 덮었다. 요청할 때의 필터를 붙잡아 두고 돌아왔을 때 달라져 있으면
버린다.

```javascript
const asked = filter;
...
if (asked !== filter) return;   // 그 사이 탭이 바뀌었다 — 새 폴링이 그린다
```

**② 카드 한 장이 던지면 목록 전체가 안 그려졌다.** 완료 카드는
`j.result.timing.detect` 를 읽는다. 옛 버전이 쓴 `job.json` 처럼 항목이 빠진
기록이 하나라도 섞이면 `TypeError` 가 나고, 그게 `poll()` 을 뚫고 나가
**폴링이 그 자리에서 멈춘다.** 화면이 얼어붙는데 서버는 멀쩡하니 원인을 찾기도
어렵다. 기본값을 깔고, 카드 한 장을 `try/catch` 로 감쌌다. 실패한 카드는
'표시 오류' 로 남고 나머지는 정상적으로 그려진다.

**③ 화면 전환이 절반만 되고 있었다.**

```css
.card{display:flex}        /* 우선순위 0,1,0 */
[hidden]{display:none}     /* 브라우저 기본값 — 우선순위 0,0,0 */
```

화면 전환은 `hidden` 속성으로 하는데, 브라우저 기본 스타일은 우리가 쓴 클래스
한 줄에 진다. 그래서 '작업' 을 눌러도 파일 브라우저가 그대로 남아 있었다.
`[hidden]{display:none !important}` 한 줄로 끝났다. 사용자가 전에
"사이드바가 하나도 동작을 안 하는 것 같다" 고 한 적이 있는데, 그때 확인한 것은
필터였고 **이 부분은 그때 못 봤다.**

## 버린 선택

**상한을 없앤다(`FA_LIST_LIMIT=0`).** 제일 쉽다. 위 표대로 3000건이면 폴링
예산의 75%를 그리는 데 쓴다. 화면이 눈에 띄게 버벅이고, 그 상태로 취소 버튼을
누르면 반응이 늦다.

**상한만 500으로 올리고 '더 보기' 를 붙인다.** 이게 내 첫 답이었고, 리뷰에서
뒤집혔다. 실측상 500건은 예산의 7% 미만이라 297건짜리 폴더는 실제로 편해진다.
하지만 **"흔한 규모" 를 기준으로 상한을 잡는 것은 규모가 커지면 반드시 다시
터지는 방식**이다. 이 서비스는 폴더를 통으로 넣으라고 만든 것이고, 폴더가
몇천 건이 되지 말라는 법이 없다. 쪽으로 나누면 그 질문 자체가 사라진다.

첫 답이 틀린 더 근본적인 이유는 따로 있다. 나는 "몇 장을 그릴까" 라는 **양의
문제**로만 봤는데, 진짜 문제는 "무엇을 그릴까" 라는 **내용의 문제**였다. 완료
기록이 할 일 목록에 섞여 있는 한, 상한을 얼마로 잡든 배치 후반에는 목록이
쓸모없어진다.

**`GET /api/jobs` 응답을 `{counts, rows}` 객체로 바꾼다.** 한 번의 왕복에 다
담을 수 있어 깔끔해 보인다. 그런데 이건 **목록이 집계를 소유하게 만드는** 것이라
방금 분리한 것을 도로 붙이는 셈이고, 배열을 기대하는 기존 클라이언트와 테스트가
전부 깨진다. 집계는 상태(`/api/status`)의 일로 두는 편이 맞다.

**WebSocket 으로 밀어 준다.** 폴링을 없애면 잘라 보내는 문제 자체가 옅어진다.
하지만 워커가 하나이고 상태 변화가 초당 몇 번 수준이라 폴링으로 충분하고,
연결 관리·재연결·다중 탭이 통째로 새 문제로 들어온다. 지금 규모에서는 대가가
이득보다 크다.

## 검증

테스트 셋. 고치기 전 코드로 되돌려 앞의 둘이 실패하는 것을 확인했다.

| 무엇을 지키는가 | 되돌리면 |
|---|---|
| 120건 중 오래된 것이 돌 때 목록 맨 위가 그 수행중 건이다 | 실패 (창 밖) |
| `/api/status` 의 집계가 목록 창과 무관하게 전체를 센다 | 실패 (`KeyError: 'counts'`) |
| 상태로 좁히면 그 상태만, 끝난 것은 최근 것부터 | 통과 — 서버측 필터는 원래 있었고, 안 쓰던 쪽이 화면이었다 |

세 번째가 되돌려도 통과한다는 점을 그대로 적어 둔다. 그 항목이 잡는 것은
**화면이 기대는 계약**이지 이번 버그가 아니다. 통과하는 테스트를 "이것도 이
버그를 잡는다" 고 세면 검증이 실제보다 두꺼워 보인다.

```
240 passed
```

화면 쪽은 297건 상태를 헤드리스 브라우저로 실제로 그려서 확인했다. 고치기 전과
같은 데이터에서 이렇게 나온다.

```
전체 남은 시간   3:22:22        남은 작업 293건
수행중 · 대기    1 / 292        K_00004_...mp4
완료             4              평균 0:41
처리 속도        4.70 × 실시간
작업                            100 / 297건
```

'완료' 탭으로 좁혀도 왼쪽 진행 상황은 여전히 수행중을 보여 준다 — 이게
`st.running` 을 목록보다 먼저 보게 만든 이유다.

## 배운 것

**목록은 표현이고, 집계는 사실이다.** 이 둘을 같은 배열 하나로 처리한 것이
원인 전부다. 화면에 창을 씌우는 순간 그 창 안에서 통계를 내면 안 된다 — 창은
"보여 줄 만큼" 이라는 표현 계층의 결정이고, 통계는 그것과 무관해야 한다.

**정렬 기준은 도메인의 순서를 따라야 한다.** 작업 큐 화면에서 "최신순" 은 틀린
기본값이었다. 큐에서 사람이 알고 싶은 순서는 **처리되는 순서**다. 목록을 만들
때 `-created` 를 쓴 건 다른 화면들의 관성이었고, 그게 처리 순서와 정반대라는
것을 100건을 넘겨 보기 전까지 몰랐다.

**규모를 넘겨 보기 전에는 모른다.** 이 코드는 테스트를 240개 통과하고 있었고,
그중 목록 테스트도 있었다(`limit=2` 로 자르는지 확인한다). 하지만 **상한보다 큰
입력을 넣어 본 테스트는 없었다.** 상한이 있는 코드에는 상한을 넘긴 테스트가
같이 있어야 한다.

**화면이 조용히 자르면 그건 거짓말이다.** 297건 중 100건을 보여 주는 것은
합리적인 결정이지만, 그 사실을 안 적으면 사용자는 100건이 전부라고 읽는다.
자를 거면 자른 만큼을 말해야 한다.

**"얼마나 보여 줄까" 보다 "무엇을 보여 줄까" 가 먼저다.** 처음에 나는 상한을
100에서 500으로 올리는 답을 냈다. 실측까지 붙여서 근거도 갖췄는데, **잘못된
질문에 정확하게 답한 것**이었다. 완료 기록이 할 일 목록에 섞여 있는 한 상한을
얼마로 잡아도 배치 후반에는 목록이 못 쓰게 된다. 숫자를 재기 전에 그 목록이
누구의 어떤 질문에 답하는지를 먼저 정했어야 했다.

**화면은 실제 규모로 그려 봐야 한다.** 덤으로 걸린 셋은 전부 "고친 게 맞나"
확인하려고 297건 상태를 헤드리스 브라우저로 띄우다가 나왔다. 그중 둘(폴링 경합,
카드 예외)은 **증상이 '화면이 멈춘다'** 라서, 서버 로그만 보면 아무 일도 없는
것처럼 보인다. 눈으로 클릭해 보는 것과 데이터를 넣고 그려 보는 것은 다르다.
