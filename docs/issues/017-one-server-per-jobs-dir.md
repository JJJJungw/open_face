# 017 — 문서는 `--workers N` 을 지원한다고 했고, 코드는 아니었다

016 에서 "판단이 필요하다" 로 남긴 넷 중 하나다. 남긴 이유는 고르는 문제였기
때문이다 — **제대로 지원할 것인가, 못 박고 문서를 고칠 것인가.**

## 무엇이 어긋나 있었나

README 와 코드 주석 여섯 군데가 `--workers N` 을 전제로 쓰여 있었다. "여러 개를
띄운다면 `FA_RECOVER=0` 으로 한 프로세스만 켜라" 처럼, **쓰는 법까지 적혀
있었다.** GPU 잠금도 프로세스 간으로 만들어 두었으니 준비가 된 것처럼 보인다.

그런데 실제로 띄우면 셋이 깨진다. 셋 다 **소리가 없다는 것**이 공통점이다.

### ① 정리가 남이 렌더 중인 폴더를 지운다

`sweep_temp()` 은 작업 폴더 안의 `.anon-*` 임시 디렉터리를 치운다. 지워도 되는지는
이렇게 판단한다.

```python
with LOCK:
    live = jid in JOBS and JOBS[jid].status == "running"
if live:
    continue        # 지금 쓰고 있는 것은 건드리지 않는다
```

`JOBS` 는 **이 프로세스의 메모리**다. B 가 돌리는 작업은 A 의 `JOBS` 에 없으므로
`live` 가 거짓이 되고, A 는 B 가 **지금 프레임을 쓰고 있는 디렉터리를 통째로
지운다.** B 는 자기 출력이 사라진 것을 인코딩 단계에 가서야 알거나, 못 알아챈다.

### ② 취소가 200 을 주면서 아무 일도 안 한다

`find_job()` 은 메모리에 없으면 디스크에서 읽어 온다 — 재시작을 견디려고 넣은
동작이다. 그래서 A 의 `/cancel` 은 B 가 돌리는 작업을 **찾는 데 성공한다.**

```python
j = jobs.find_job(jid)          # 디스크에서 읽은 사본
with jobs.LOCK:
    j.cancel = True             # A 의 메모리에 있는 사본에 찍는다
jobs.save_job(j)                # job.json 에 쓴다
return jobs.snapshot(j, ...)    # 200
```

B 는 자기 메모리의 `Job` 객체만 본다. 디스크를 다시 읽지 않는다. 게다가 B 는
0.5초마다 진행률을 `job.json` 에 흘려 쓰므로, **A 가 찍은 취소 표시를 덮어
지운다.** 사람은 취소 버튼을 눌렀고 200 을 받았고 화면에도 반영됐는데, 영상은
끝까지 처리돼서 결과 버킷에 올라간다.

배치를 잘못 넣어서 `cancel-all` 을 누르는 것은 일상적인 조작이다.

### ③ 복구가 같은 작업을 N번 처리한다

기동할 때 `recover_orphans()` 가 `queued` 를 다시 큐에 넣는다. `--workers 4` 면
네 프로세스가 각자 기동하면서 각자 전부 다시 넣는다. 같은 영상이 네 번
처리되고, 네 번 같은 결과 키로 올라가고, GPU 시간은 네 배로 든다.

문서가 안내한 `FA_RECOVER=0` 은 이걸 **일부만** 막는다. 셋 중 하나만 덮고,
게다가 그러면 진짜로 필요할 때 복구가 안 도는 프로세스가 셋 생긴다.

## 무엇을 골랐나

**못 박기로 했다.** 이유는 셋이다.

첫째, 제대로 지원하려면 작업 소유권을 프로세스 간에 나누는 장치가 필요하다 —
작업마다 소유자 표시와 임차 기간, 취소는 파일 신호나 별도 채널, 정리는 소유자
아닌 프로세스가 손대지 않는 규칙. 그건 작은 일이 아니고, **얻는 것이 거의
없다.**

둘째가 그 이유다. **추론은 어차피 GPU 한 장 위에서 직렬화된다.** 프로세스를 넷
띄워도 넷이 GPU 잠금 앞에 줄을 설 뿐이고, VRAM 은 넷이 나눠 쓰므로 배치 크기가
줄어 오히려 느려진다. `--workers N` 이 이득인 것은 요청 처리가 CPU 병목인
서비스인데, 우리는 요청 하나가 수십 초짜리 GPU 작업이다.

셋째, **틀린 문서는 없는 문서보다 나쁘다.** 남이 클론해서 문서대로 하면 밟는다.

## 어떻게 막는가

`jobs.claim_jobs_dir()` 이 기동할 때 작업 폴더에 `.server.lock` 을 만들고
`flock` 을 잡는다. 이미 다른 프로세스가 들고 있으면 그 pid 와 함께 무엇을
하라는지를 적어 거절한다.

```
작업 폴더를 다른 서버가 쓰고 있습니다 (pid 31544): /home/ubuntu/face-anonymizer/jobs
이 서비스는 작업 폴더 하나에 프로세스 하나만 지원합니다. uvicorn 을 --workers
없이 띄우거나, 두 번째 서버에는 FA_JOBS_DIR 로 다른 폴더를 주세요.
```

`flock` 을 고른 이유는 **죽은 프로세스의 잠금이 남지 않기 때문**이다. pid 파일로
하면 하드 킬 뒤에 파일이 남아 다음 기동을 막고, 그러면 "잠금 파일을 지우세요"
라는 안내를 또 적어야 한다. 커널이 놓아 주는 쪽이 손이 덜 간다.

**두 가지는 거절하지 않는다.** 잠글 수단이 아예 없는 경우(윈도우, 읽기 전용
볼륨)는 경고만 남기고 지나간다 — 그건 "둘이 돌고 있다" 가 아니라 "확인할 방법이
없다" 이고, 확인이 안 된다고 서버를 못 뜨게 하는 것은 과하다. 그리고 무중단
재시작처럼 내려가는 쪽과 올라오는 쪽이 잠깐 겹치는 것은 정상이라 5초까지
기다린다. 여기서 곧바로 거절하면 **배포할 때마다 서버가 안 뜬다.**

작업 폴더를 나눠 주면 두 서버는 여전히 뜬다. 그건 막을 이유가 없다.

## 남은 것

**GPU 잠금은 작업 폴더에 묶여 있다.** 한 대에 두 서버를 각자 다른
`FA_JOBS_DIR` 로 띄우면 서로의 GPU 잠금을 못 본다 — 잠금 파일 경로가
`<FA_JOBS_DIR>/.gpu.lock` 이기 때문이다. 지금은 한 대 한 서버가 전제라
문제가 안 되지만, 그 전제를 깰 거면 잠금 경로를 따로 열어야 한다.
