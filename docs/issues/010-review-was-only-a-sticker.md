# 010 검수 딱지를 붙여 놓고 상태는 '완료'로 두던 문제

## 증상

얼굴이 하나도 검출되지 않은 영상이 **완료 목록에 그대로 섞여 있었다.**

008 에서 "검출 0건이면 사람이 봐야 한다" 는 판단을 넣었는데, 그때 만든 것은
**딱지**뿐이었다. 결과에 경고 문자열이 붙고 화면 카드에 배너가 뜨는 것까지가
전부였고, 작업 상태는 여전히 `done` 이었다.

그래서 실제로는 이렇게 된다.

- 완료 건수가 그 영상을 센다 — "몇 건 납품 가능한가" 가 틀린 숫자가 된다
- 완료 탭에 다른 수백 건과 나란히 놓인다. 배너는 카드를 열어야 보인다
- 폴더 진척률이 100% 가 된다. 아무도 안 봤는데 폴더가 끝난 것으로 보인다
- 결과물이 `_deid` 폴더에 올라가 있으므로 그 폴더를 통으로 넘기면 **비식별화가
  하나도 안 된 원본이 납품된다**

배너는 사람이 그 카드를 열어야 보이는 것이고, 300건짜리 배치에서 완료 카드를
하나씩 열어 보는 사람은 없다.

## 왜 놓쳤나

008 을 만들 때 **MSA 경로만 보고 있었다.** 그쪽은 완료 보고에 `review_needed`
를 실어 보내고 "저쪽이 검수로 라우팅해 주세요" 라고 요청 목록에 적는 것으로
끝난다 — 판정하는 주체가 우리가 아니기 때문이다.

API 경로는 **우리가 그 주체다.** 그런데 같은 구조를 그대로 가져오면서, 판정을
넘길 상대가 없다는 것을 놓쳤다. `job_runner.review_of()` 는 `service/` 어디에서도
불리지 않고 있었다.

## 고친 방식

**상태를 하나 늘렸다.** `queued → running → review → done`.

```
STATUSES = ("queued", "running", "review", "done", "failed", "cancelled")
```

사람이 봐야 하는 사유가 하나라도 있으면 워커가 `done` 대신 `review` 로 멈춘다.
`done` 이 되는 길은 **검수 승인 하나뿐**이다.

```
POST /api/jobs/{jid}/review   {"action": "approve" | "reject", "note": "..."}
```

`approve` → `done`, `reject` → `failed`. 어느 쪽이든 판정 시각과 사유가
`job.json` 과 저널(`job.reviewed`)에 남는다. 두 번째 판정은 409 로 막는다 —
받아 주면 완료된 건을 나중에 조용히 실패로 바꿀 수 있다.

사이드바에 `검수` 탭이 생겼고, 목록 정렬에서 **대기보다 위**에 둔다. 아래로
내리면 300건짜리 배치에서 검수 두 건이 완료 기록에 파묻혀 영영 안 보인다.

## 곁따라 바뀐 것들

**검수 중에도 결과물을 받을 수 있다.** `GET /api/jobs/{jid}/download` 가
`done` 만 허용하고 있었다. 판정하려면 봐야 한다.

**폴더 진척률에서 검수 대기는 '남은 것'이다.** 검수가 끝나야 폴더가 끝난 것이다.

## 일부러 안 한 것

**반려해도 버킷의 결과물을 지우지 않는다.** 지우는 것은 되돌릴 수 없고, 반려
사유가 "설정을 바꿔 다시 처리하면 될 것" 일 수도 있다. 대신 결과물 키를 응답과
저널에 남겨서, 납품 폴더에서 빼는 판단을 사람이 하게 한다.

여기에는 **아직 구멍이 있다.** 반려된 결과물이 `_deid` 폴더에 그대로 남으므로,
그 폴더를 통으로 넘기면 반려된 파일이 같이 간다. 자동 삭제를 넣을지, 반려된
키 목록을 내려주는 API 를 만들지는 정해야 한다.

(처음에는 검수 대기 중 로컬 사본도 붙들게 했다가 되돌렸다 — 아래 참고.)

**'다시 처리' 판정은 넣지 않았다.** 검출 0건의 흔한 원인이 conf·회전·해상도라
재처리가 자연스러운 세 번째 선택지지만, 지금은 승인/반려 둘로 두었다. 반려한
뒤 다시 제출하면 같은 일이 된다.

## 처음 판에 있던 구멍들

만들고 나서 다시 훑어 네 개를 고쳤다. 전부 "검수라는 상태를 새로 만들었는데,
그 상태를 모르는 코드가 남아 있었다" 는 한 가지 원인이다.

**TTL 이 검수 대기 건을 지웠다.** `sweep()` 은 status 로 기간을 고르는데 그
분기에 `review` 가 없어서 일반 TTL(기본 2시간)을 탔고, `j.finished` 는 검수로
들어가는 순간 찍힌다. 밤에 300건 돌려 놓고 아침에 오면 검수 목록이 비어 있고
결과물만 `_deid` 에 남는다 — 이 기능의 목적이 통째로 무효가 되는 자리다.
`FA_REVIEW_TTL_MIN` 을 두고 **기본 0(안 지움)** 으로 했다.

**반려한 파일을 다시 처리할 수 없었다.** 반려해도 버킷 결과물은 남기는데,
`skip_processed` 가 그걸 보고 '이미 처리됨' 으로 걸렀다. 반려 → 설정 바꿔
재제출 → `409`. 반려의 유일한 후속 조치가 막혀 있었다. `jobs.rejected_inputs()`
로 반려된 입력만 그 대조에서 뺀다 — 다시 돌리면 결과물이 덮어써진다.

**검수 대기가 로컬 디스크를 붙들었다.** "보지 않고는 판정할 수 없다" 며 정리를
건너뛰게 했는데, 다운로드 라우트가 이미 "로컬에 없으면 S3 로 302" 다. 붙들
이유가 없었고, 붙들면 검수가 밀린 만큼 디스크가 차서 결국 **새 작업 제출이
거부된다**(001 이 그 형태로 되살아난다). 원래 정리 정책으로 되돌렸다.

**재시작하면 검수 건이 집계에서 사라졌다.** `recover_orphans()` 는
`queued`·`running` 만 메모리에 올리고 `counts()` 는 메모리만 본다. 그래서 재시작
뒤 사이드바 검수 배지는 0인데 탭을 열면 목록이 나왔다. 복구가 `review` 도
메모리에 올리되 **워커에는 제출하지 않는다** — 처리는 끝났고 남은 것은 사람의
확인이다.

## 그다음에 막은 것들

**검수 건에 `/cancel` 과 `DELETE` 가 열려 있었다.** 화면엔 버튼이 없지만 API 는
막지 않았다. 취소는 받아 줘도 상태가 안 바뀌는데(취소는 대기 건만 즉시 바꾼다)
200 이 나가서 사람은 취소했다고 믿는다. 삭제는 더 나쁘다 — **판정 없이 지우면
왜 걸렸나가 같이 사라진다.** 둘 다 `job_in_review` 409 로 막고 판정으로 유도한다.

**`/api/jobs/{id}/result` 가 `done` 만 허용했다.** `download` 만 열어 둔 것은
반쪽이다 — presigned URL 로 보려는 쪽이 막힌다. 둘은 같은 목적의 두 경로다.

**판정 경쟁.** 상태 확인이 락 밖이라 탭 두 개에서 동시에 누르면 둘 다 통과하고,
나중 것이 앞의 판정을 덮어썼다. 승인해 둔 건이 조용히 실패로 바뀔 수 있다.
확인과 변경을 한 락 안으로 넣었다.

**두 화면이 다른 말을 했다.** 검수는 `active`(수행중+대기)에 없어서 HUD 가
'유휴' 라고 하는데, 폴더 진척률은 검수를 '남은 것' 으로 센다. `active` 를
건드리지 않고 — 검수는 워커가 아니라 사람이 할 일이라 그 정의가 맞다 — HUD 가
'검수 대기 N건' 을 말하고 그 화면으로 가는 길을 놓는 쪽으로 맞췄다.

`cancel_all` 은 검수를 건드리지 않는다. 취소는 "아직 안 한 일을 안 하겠다" 이고
검수는 처리가 끝나 결과물까지 올라간 상태다. 같이 지우면 비식별화가 안 된
파일이 버킷에 남은 채 기록만 사라진다.

## 아직 남은 것

- 검수로 보내는 조건에 **검출률 1% 미만**이 포함된다. 실제 데이터에서 검수
  건수가 얼마나 되는지 재 보지 않았다 — 300건 중 100건이 오면 아무도 안 본다
- 반려된 결과물이 `_deid` 폴더에 남는다(위 '일부러 안 한 것' 참고)

## MSA 경로는 그대로다

그쪽은 여전히 `ok=true` + `review_needed=true` 로 보고한다. 판정하는 주체가
저쪽 시스템이고 우리에게는 그 사람도 그 화면도 없다. 이 문서의 변경은 **우리가
서버일 때**의 이야기다.
