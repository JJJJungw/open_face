# 008 · 얼굴을 하나도 못 찾아도 "비식별화 완료" 로 나간다

**상태** 해결됨

**한 줄** 검출 0건이면 원본이 그대로 출력되는데, 큐 경로에서는 그 사실이 보고에
실리지 않는다. 저쪽은 `ok=true` 만 보고 `done` 으로 넘긴다 — **비식별화가 하나도
안 된 원본이 '비식별화 완료' 로 납품된다.**

## 증상

파이프라인은 이미 알고 있었다.

```python
if raw_boxes == 0:
    warnings.append("no-detections")
    log.error("검출 0건 — 원본이 그대로 출력된다. conf/imgsz/가중치/영상 회전을 확인할 것.")
```

웹 화면은 이 경고를 카드에 배너로 띄운다. 그런데 MSA 잡 러너의 응답은 이렇다.

```json
{"elapsed_s": 49.6,
 "targets": [{"label": "deid-720p", "frames": 1027, "detected_frames": 0,
              "realtime_factor": 0.7}]}
```

`warnings` 가 없다. `detected_frames: 0` 이 들어 있긴 하지만, **그걸 읽으라고 아무
데도 적혀 있지 않다.** 받는 쪽 입장에서 그건 통계지 신호가 아니다.

## 재현

얼굴을 못 찾는 상황을 만들고(가중치 손상·회전된 영상·잘못된 imgsz 중 아무거나)
잡을 하나 넣는다. 완료 보고는 `ok=true` 로 온다.

## 원인

**같은 정보가 두 경로에서 다르게 취급됐다.** 웹 화면을 만들 때는 "결과를 그대로
믿으면 안 되는 사유" 를 `Result.warnings` 로 뽑아 화면까지 올렸다. 큐 경로는
나중에 만들었고, 응답을 설계할 때 **저쪽이 무엇을 필요로 하는지가 아니라 우리가
무엇을 갖고 있는지**로 필드를 골랐다. 처리 시간·프레임 수·속도 — 전부 성능
숫자다. 품질 신호는 빠졌다.

여기에 판단이 하나 얽혀 있다. 검출 0건은 **오류가 아니다.** 얼굴이 없는 풍경
영상은 0 이 정당한 결과이고, 그걸 실패로 던지면 멀쩡한 영상이 재시도 상한까지
돌다가 실패로 떨어진다. 그래서 파이프라인은 예외를 안 던지고 경고만 남기게 되어
있었다 — 그 설계는 맞았는데, **경고를 받을 사람이 큐 경로에는 없었다.**

## 영향

**화질 문제가 아니라 개인정보 사고다.** 이 서비스의 산출물은 방송 자료의 얼굴을
가린 영상이고, 가려지지 않은 영상이 '가려짐' 딱지를 달고 다음 공정으로 넘어간다.
검수 단계가 사람 눈으로 전량을 다시 보지 않는 한 걸러지지 않는다.

검출이 0이 되는 경로는 하나가 아니다.

| 경로 | 결과 |
|---|---|
| 진짜로 얼굴이 없는 영상 | 정상 — 원본 그대로가 맞다 |
| 회전 메타데이터가 붙은 세로 영상 | 얼굴이 90도 누워 있어 못 잡는다 |
| 가중치가 잘못 받아졌다 | 전량 0 |
| imgsz·conf 가 그 소재에 안 맞는다 | 전량 0 또는 극소 |
| HDR 톤매핑 실패로 화면이 뭉갠다 | 전량 0 |

첫 줄만 정상이고 나머지 넷은 사고다. **코드는 다섯을 구분할 수 없다.**

## 해결

**실패로 던지지 않는다. 딱지를 붙여 성공과 함께 보낸다.**

```python
REVIEW = {
    "no-detections":
        "얼굴이 하나도 검출되지 않았습니다. 원본이 그대로 나갔습니다 — "
        "얼굴이 없는 영상이 맞는지 한 번 확인해 주세요.",
    ...
}
```

응답이 이렇게 바뀐다.

```json
{"elapsed_s": 49.6,
 "review_needed": true,
 "review": [{"code": "no-detections", "detail": "no-detections",
             "message": "얼굴이 하나도 검출되지 않았습니다. 원본이 그대로 …"}],
 "notices": [],
 "targets": [{"label": "deid-720p", "detected_frames": 0,
              "detection_rate": 0.0, "warnings": ["no-detections"]}]}
```

`ok` 는 여전히 `true` 다. 처리는 성공했고, 필요한 것은 **재시도가 아니라 사람의
확인**이기 때문이다. 실패로 보내면 저쪽이 같은 영상을 세 번 더 돌리고 결과는 매번
같다 — GPU 만 태우고 사람은 여전히 안 본다.

### 사람을 부를 것과 아닌 것을 가른다

경고가 여섯 종류인데 성격이 다르다. 전부 사람을 부르면 딱지가 의미를 잃는다.

| 경고 | 어디로 | 왜 |
|---|---|---|
| `no-detections` | **검수** | 원본이 그대로 나갔을 수 있다 |
| `low-detection-rate` | **검수** | 회전·해상도·임계값으로 놓쳤을 수 있다 |
| `decode-partial` · `decode-short` | **검수** | 결과물 뒷부분이 빠졌을 수 있다 |
| `decode-unverified` | 참고 | 프레임 수를 못 세었을 뿐이다 |
| `audio: …` | 참고 | 영상은 정상이다 |

수치는 요약하지 않고 `detail` 에 원문 그대로 남긴다. `low-detection-rate` 만 남기고
`0.50%` 를 버리면 나중에 "얼마나 낮았는데?" 에 답할 수 없다.

딱지는 **타깃별이 아니라 영상 단위**로 모은다. 저쪽이 판정하는 단위가 `video_id`
이고, 같은 영상의 타깃 둘에 같은 딱지가 두 번 붙어 봐야 사람이 볼 것은 하나다.

## 버린 선택

**`min_detection_rate` 로 실패시키기.** 파이프라인에 이미 있는 기능이다. 얼굴이
반드시 있는 데이터셋이라면 이게 맞는데, 방송 자료에는 풍경·자료화면·타이틀이
섞여 있다. 임계값을 어디에 두든 정상 영상이 실패로 떨어진다.

**`detected_frames` 를 보고 저쪽이 판단하게 두기.** 이미 보내고 있던 값이다.
그런데 그건 통계지 신호가 아니다 — **받는 쪽이 그 필드의 의미를 알아야만**
동작하는 계약은, 아는 사람이 팀을 떠나는 순간 조용히 깨진다. 우리가 이미 판단해서
"봐 달라" 고 말해 주는 편이 싸다.

**결과물에 워터마크나 표식을 남기기.** 산출물 자체에 흔적을 남기면 확실하지만,
납품물을 오염시킨다.

## 검증

테스트 넷.

| 무엇을 지키는가 |
|---|
| 검출 0건이 `review_needed=true` 로 오되 **실패가 아니다**(결과물은 올라간다) |
| 정상 결과에는 딱지가 안 붙는다 |
| 참고용 경고(`audio`·`decode-unverified`)는 사람을 부르지 않는다 |
| 껍데기가 딱지를 **성공 메시지에 실어** 보낸다 (`ok=true` + `review_needed=true`) |

## 배운 것

**응답 필드를 우리가 가진 것으로 고르면 안 된다.** 처리 시간·프레임 수·속도를
넣은 건 우리가 그걸 재고 있었기 때문이다. 받는 쪽이 무엇을 판단해야 하는지에서
출발했다면 "이 결과를 믿어도 되나" 가 첫 필드였을 것이다.

**같은 정보를 두 경로가 다르게 취급하면 나중 것이 진다.** 웹 화면에는 경고 배너가
있었다. 큐 경로를 만들 때 화면이 무엇을 띄우는지 다시 보지 않았다. 새 진입점을
만들 때는 **기존 진입점이 사용자에게 무엇을 말해 주고 있었는지**를 목록으로
확인해야 한다.

**"오류가 아니다" 와 "괜찮다" 는 다르다.** 검출 0건을 예외로 던지지 않기로 한
판단은 옳았는데, 거기서 멈추면 아무 일도 없었던 것이 된다. 오류로 만들지 않기로
했다면 **대신 무엇으로 만들지**를 같이 정해야 한다.
