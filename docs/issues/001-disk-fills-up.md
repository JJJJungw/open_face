# 001 · 처리가 끝나도 로컬 파일이 남아 디스크가 찬다

**상태** 해결됨

**한 줄** S3 작업이 끝나 결과물을 올린 뒤에도 입력·출력 파일이 로컬에 남고,
실패한 작업은 아예 안 지워진다. 대량 처리를 시작하면 디스크가 먼저 찬다.

## 증상

아직 겪지 않았다. 지금까지 단건씩만 돌렸기 때문이다. 코드를 읽다 발견했고,
대량 처리를 시작하면 반드시 물린다고 판단해 먼저 기록한다.

작업 디렉터리를 보면 처리가 끝난 뒤에도 입력과 출력이 그대로 있다.

```
jobs/dbffab7515e6/
├── input.mp4                                 원본 (S3 에서 받은 것)
├── K_00000_00_0000000_0034342_deid.mp4       결과물 (S3 에 이미 올림)
└── job.json
```

## 재현

```bash
# S3 키 하나를 제출하고 끝날 때까지 기다린 뒤
ls -lh jobs/$(ls -t jobs | head -1)
```

결과물이 S3 에 올라갔는데도 두 파일이 남아 있다.

## 원인

`service/worker.py` 의 `run()` 은 업로드에 성공한 뒤 상태만 `done` 으로 바꾸고
파일은 건드리지 않는다. 정리는 전적으로 TTL 청소(`jobs.sweep()`)에 맡겨져 있다.

그런데 그 청소가 두 군데서 새고 있다.

**첫째, 완료된 작업도 `FA_JOB_TTL_MIN`(기본 120분) 동안 남는다.** 결과물을 이미
S3 에 올렸으므로 로컬 사본은 "혹시 다시 받을까 봐" 두는 것인데, 실제로는
`GET /api/jobs/{id}/download` 가 로컬에 없으면 S3 로 302 리다이렉트하도록 이미
되어 있다. 즉 **없어도 되는 파일을 2시간 들고 있다.**

**둘째, 실패한 작업은 영원히 안 지운다.**

```python
# service/config.py
FAILED_TTL = int(os.environ.get("FA_FAILED_TTL_MIN", 0)) * 60   # 0 = 안 지움
```

이건 의도한 것이다 — "배치로 수백 건 돌린 뒤 몇 건이 실패했을 때, 입력과 사유가
남아 있어야 원인을 볼 수 있다." 판단 자체는 맞다. 문제는 **원인을 보는 데 필요한
것은 `job.json` 뿐인데 입력 영상까지 같이 남긴다**는 점이다.

여기에 하나가 더 겹친다. 디스크 여유 검사가 **제출 시점에만** 있다.

```python
# service/server.py — create_jobs() 안
check_admission()          # 여기서 한 번
...
for key in keys:
    worker.enqueue(...)    # 500건이 한꺼번에 들어간다
```

500건을 한 번에 넣으면 그 순간 한 번만 확인하고, 이후 몇 시간에 걸쳐 처리되는
동안에는 아무도 디스크를 보지 않는다.

## 영향

결과물은 3.5 Mbps 고정이므로 크기가 계산된다.

| 클립 길이 | 결과물 | 입력(원본 비트레이트에 따라) | 한 건 합계 |
|---|---|---|---|
| 1분 | 26 MB | 8~15 MB | 약 40 MB |
| 5분 | 131 MB | 40~75 MB | 약 200 MB |

**완료분** — 5분 클립을 시간당 12건 처리한다면 TTL 120분 동안 24건이 항상
디스크에 있다. 약 4.8 GB. 이건 회전하므로 상한이 있다.

**실패분** — 회전하지 않는다. 500건 배치에서 10%가 실패하면 50건 × 200 MB =
**10 GB 가 영구히 남는다.** 배치를 두 번 돌리면 20 GB 다.

가장 나쁜 시나리오는 이렇다. 대량 배치 중간에 디스크가 임계치 아래로 떨어진다.
그런데 제출은 이미 끝났으므로 `507` 로 막지 못하고, 남은 수백 건이 **전부 실패**
한다. 그리고 그 실패들이 다시 입력 파일을 남기면서 디스크를 더 먹는다.

## 해결

네 조각으로 나눠 고쳤다. 판단 기준은 **"로컬 사본이 유일한 사본인가"** 하나다.

### 1. S3 업로드에 성공하면 로컬 사본을 바로 지운다

```python
# service/worker.py — 업로드와 done 처리 뒤
if j.s3_key and j.s3_output and not config.KEEP_LOCAL:
    jobs.drop_media(j, "S3 업로드 완료")
```

근거는 다운로드 라우트에 **이미** 있었다.

```python
if not j.output or not os.path.exists(j.output):
    # 로컬 사본은 정리됐어도 S3 원본은 남아 있다.
    return RedirectResponse(store.presigned_url(j.s3_output), status_code=302)
```

"로컬에 없어도 된다" 를 상정하고 짜 놓고 **정작 그 상황을 만드는 코드를 안
만든 것**이 이 문제의 정체였다. 지우는 편이 원래 의도에 맞고, GPU 서버가 파일
전송을 떠안지 않아 부하도 준다.

`FA_KEEP_LOCAL_RESULT=1` 로 되돌릴 수 있게 뒀다.

### 2. 최종 실패한 S3 작업은 기록만 남긴다

실패를 안 지우던 것은 의도였다 — "원인을 보려면 남아 있어야 한다". 그 판단은
맞았고, 틀린 것은 **무엇을 남겨야 하는가**였다. 원인 파악에 쓰는 것은 사유·
단계·시도 횟수이고 전부 `job.json` 에 있다. 영상 자체가 원인일 때도 원본은
버킷에 그대로다. 200MB 를 몇 KB 때문에 붙들고 있을 이유가 없다.

재시도 중에는 지우지 않는다. 최종 실패일 때만이다.

### 3. 작업 시작 전에 디스크를 본다

부족하면 **정리를 한 번 강제로 돌리고** 다시 본다. TTL 지난 것이 남아 있으면
그때 회수된다. 그래도 부족하면 그 작업을 507 로 실패시킨다.

여기는 반쪽이다. 제대로 하려면 "잠시 멈췄다가 여유가 생기면 재개" 여야 하는데,
그건 재시도를 **시각 기준으로 스케줄**하는 구조가 있어야 한다.
[003](003-retry-without-backoff.md) 에서 백오프를 만들 때 같이 붙인다. 지금
억지로 만들면 스케줄러를 반쯤 짓게 된다.

### 4. 죽은 프로세스가 남긴 임시 디렉터리를 정리 대상에 넣는다

파이프라인은 작업 폴더 안에 `.anon-*` 를 만들고 `finally` 에서 지운다. 강제
종료되면 그 `finally` 가 안 돈다. 정리 주기에 같이 훑되 **지금 쓰고 있는 것은
건드리지 않는다** — 그 작업이 깨진다.

## 버린 선택

**전부 다 지우기.** 직접 업로드분까지 지우면 결과물이 어디에도 없어진다.
`j.s3_key` 유무로 가른 이유다.

**보관 기간을 줄이기(120분 → 10분).** 손이 제일 덜 가지만 근본이 아니다.
회전량이 줄 뿐 여전히 필요 없는 파일을 들고 있고, 실패분은 그대로 남는다.

**디스크가 부족하면 큐를 멈추기.** 맞는 방향이지만 지금 구조로는 "멈춤" 을
표현할 수단이 없다. 즉시 재큐하면 CPU 를 태우는 무한 루프가 된다.

## 검증

테스트 여덟 개를 붙였고, 각각 고친 코드를 되돌려 실제로 깨지는지 확인했다.

| 무엇을 지키는가 |
|---|
| S3 작업이 끝나면 작업 폴더에 `job.json` 만 남는다 |
| 로컬 사본이 없어도 다운로드가 302 로 S3 를 준다 |
| `FA_KEEP_LOCAL_RESULT=1` 이면 예전처럼 남는다 |
| **직접 업로드분은 지우지 않는다** — 지우면 결과가 사라진다 |
| 최종 실패한 S3 작업은 `job.json` 만 남고 사유는 그대로다 |
| 정리가 `.anon-*` 를 치운다 |
| **돌고 있는 작업의 임시 디렉터리는 안 치운다** |
| `drop_media()` 가 회수한 바이트를 정확히 보고한다 |

효과는 이렇게 바뀐다.

| | 고치기 전 | 고친 뒤 |
|---|---|---|
| 완료분 (회전) | 5분 클립 24건 × 200MB ≈ 4.8 GB | `job.json` 만 (수십 KB) |
| 실패분 (영구) | 50건 × 200MB = 10 GB | `job.json` 만 |

## 배운 것

**"나중에 지울 수 있게" 짜 놓고 지우는 쪽을 안 만드는 일이 흔하다.** 다운로드
라우트의 302 폴백은 처음부터 있었고 주석에도 "로컬 사본은 정리돼도" 라고 적혀
있었다. 이건 설계 실수가 아니라 **절반만 구현된 설계**였다. 폴백 경로를 만들 때
"그 상황을 실제로 만드는 코드가 있는가" 를 같이 물었어야 했다.

**의도한 동작과 그 의도의 범위는 다르다.** 실패를 안 지우는 것은 의도였지만
"영상까지" 는 의도가 아니었다. 결정을 남길 때 무엇을 위한 결정인지까지 적어야
이런 것이 드러난다.
