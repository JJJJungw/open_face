# 015 — 맥에서 올린 파일 이름 하나가 처리를 통째로 막았다

## 증상

```
서버 내부 오류가 발생했습니다
[Errno 36] File name too long:
'/home/ubuntu/face-anonymizer/jobs/757df94f1b7d/EP12-13 ※광일이 명장면※ …_deid.mp4'
일시적인 오류로 보고 4회까지 다시 시도했지만 계속 실패했습니다
```

## 왜 처음에 말이 안 됐나

이름을 세어 보면 **67자**다. UTF-8 로 139바이트고, ext4 한계는 255다. 실제로
그 이름 그대로 파일을 만들어 보면 잘 만들어진다. EC2 에서도 255바이트까지
문제없이 만들어졌다.

    100 OK  120 OK  130 OK  139 OK  143 OK  145 OK  150 OK  200 OK  255 OK

즉 **화면에 보인 이름으로는 이 오류가 날 수 없었다.** 로그의 원문을 재 보고
나서야 답이 나왔다.

    파일명 298바이트

## 원인 — NFD

한글은 유니코드에 두 가지로 저장될 수 있다. `광` 을 한 글자로 두는 방식(NFC,
3바이트)과 `ㄱ + ㅗ + ㅇ` 자모 셋으로 쪼개 두는 방식(NFD, 9바이트)이다. **눈에는
똑같은데 바이트가 세 배다.**

    NFC   67자  139바이트
    NFD  120자  298바이트   ← 로그에 찍힌 값과 정확히 일치

macOS 가 파일 이름을 NFD 로 저장한다. 맥에서 올린 파일은 S3 키가 NFD 로 들어가고,
우리는 그 키의 파일명을 **그대로 로컬 파일 이름으로** 썼다. 리눅스 ext4 의 255
바이트 한계에 걸린다. 한글 84자쯤부터다.

그래서 이건 그 파일 하나의 문제가 아니라 **맥에서 온 긴 한글 이름은 전부 터진다**
는 뜻이었다. 내가 처음에 139바이트로 잰 것도 함정이었다 — 화면에서 복사하면
NFC 로 정규화돼 넘어오는 경우가 많아서, 재 보면 짧게 나온다.

## 고친 방식 — 못 하는 건 거절하고, 할 수 있는 건 조용히 하되 알린다

**로컬 파일 이름은 우리 사정이다.** 입력은 이미 `input.<ext>` 로 받고 있었는데
결과물만 원본 이름을 쓰고 있었다 — 반만 적용된 상태였다. 결과물도
`output.mp4` 로 짓는다. 예쁜 이름이 필요한 자리는 **버킷 키와 내려받기 파일명**
뿐이고 둘 다 `j.name` 에서 따로 만든다.

이걸 사용자에게 "이름을 줄여 주세요" 로 안내할까 고민했는데, 그건 **우리 제약을
상대 책임으로 넘기는 일**이다. 그 파일은 이미 버킷에 있고, 이름을 바꾸려면
방송사 원본이나 그쪽 시스템을 건드려야 한다. 게다가 S3 는 키를 1024바이트까지
받으므로 결과물은 예쁜 이름 그대로 잘 올라간다 — **로컬 이름만 바꾸면 아무것도
잃지 않는다.**

**진짜 못 하는 것은 미리 거절한다.** 그런 경우가 실제로 있다. 결과물을 올릴
버킷 키가 1024바이트를 넘는 경우다(NFD 한글로 340자쯤). 이건 우리가 어떻게 해도
못 올린다. 그때는 40초를 처리한 뒤에 실패하지 않고 **제출 시점에 건별로** 돌려
준다 — 이미 있던 `rejected` 경로를 그대로 탄다.

거절 문구에는 **왜 긴지**를 같이 적는다. 글자 수만 말하면 "60자밖에 안 되는데
왜?" 가 되기 때문이다.

    결과물 주소가 1180바이트입니다 (한계 1024). 이름이 340자인데 자모가 분리된
    형태로 저장돼 있어 바이트로는 세 배가 됩니다(맥에서 올린 파일이 그렇습니다).

**조용하지 않게 한다.** 길이 말고 더 중요한 부작용이 있었다. **NFD 이름은 화면
검색에 안 잡힌다.** 사람이 치는 글자는 NFC 라 바이트가 달라서, 파일이 분명히
있는데 검색하면 안 나온다. 그것도 모르고 있으면 "왜 없지" 로만 겪는다. 검색은
양쪽을 NFC 로 맞춰 비교하게 고쳤고, 그런 이름이 섞여 있으면 제출할 때 한 줄로
알려 준다 — **실패가 아니라 알림이다.**

## 덤 — 되지도 않을 재시도를 4번 했다

이름이 길어서 나는 오류는 다시 해도 100% 같은 결과인데, `OSError` 가 `INTERNAL`
로 분류되고 그게 `retryable=True` 라 4번 재시도했다. 95초를 버리고 그동안 큐가
막혔다. 로컬 이름을 짧게 지으면서 이 경로 자체가 사라졌다.

## 같이 걷어낸 것 (코드 훑기 2번)

`docs/issues/014` 에서 미뤄 둔 "안 쓰는데 남아 있는 것" 을 이번에 처리했다.

`s3.py` 의 옛 이름 넷(`BUCKET` `REGION` `ROOT_PREFIX` `OUTPUT_PREFIX`) — 주석에
"여기저기서 읽고 있어 한 번에 안 걷어낸다" 고 적혀 있었지만 **읽는 데가 한 곳도
없었다.** `reconfigure()` 도 같이 단순해졌다.

지운 `/download` 의 흔적 — `FileResponse`·`RedirectResponse` 임포트, `a.dl` CSS,
그리고 README 에 아직 살아 있던 API 표 한 줄과 curl 예제. 남이 클론해서 그걸
따라 하면 404 를 만난다.

아무 일도 안 하던 것들 — `FA_MSA_CONCURRENCY`(상수만 있고 celery 에 안 넘어감),
`errors.FFMPEG_MISSING`(정의만 있고 어디서도 안 던지는데 `/api/problems` 로는
나가서 "이 오류가 날 수 있다" 고 거짓말을 했다), `progress.ORDER`,
`naming.STATE_RAW`, `job_runner._DOWNLOAD_SHARE`, `detector.warmup()`,
안 쓰는 임포트 열둘.

문서에서는 `.env.example` 에 두 번 나오면서 기본값이 서로 달랐던
`FA_WEIGHTS_SOURCE` 를 하나로 정리했다.

## 그 김에 — 직접 업로드 경로를 걷어냈다

로컬 이름 얘기를 하다가 나온 질문이었다. "로컬로 다운로드하는 API 자체가 없는데
왜 로컬 이름을 신경 쓰나?" 맞는 지적이고, 답은 **다운로드가 아니라 만드는
시점에 터졌기 때문**이다. 결과물을 S3 에 올리려면 먼저 디스크에 써야 한다.

그러다 더 큰 걸 봤다. **화면에 파일 업로드 버튼이 아예 없었다.** `<input
type="file">` 도 `FormData` 도 index.html 에 하나도 없다. multipart 업로드는
사람이 닿을 수 없는 API 전용 경로였고, 우리가 실제로 하는 일(버킷에서 900건)과
아무 상관이 없었다. 남겨 두면 인증을 붙일 때 같이 막아야 하고, **결과물이
버킷에 없는 작업**이라는 예외 경로를 계속 들고 다녀야 한다.

같이 빠진 것 — `create_jobs` 의 multipart 분기와 폼 파싱, `_coerce`,
`CONFLICTING_INPUT`·`EMPTY_FILE`·`PAYLOAD_TOO_LARGE` 오류 셋,
`FA_MAX_UPLOAD_MB`·`CHUNK` 설정, `/result` 의 `via: local` 분기,
`python-multipart` 의존성.

**테스트를 먼저 옮기고 나서 지웠다.** 34개가 그 경로로 파이프라인을 돌리고
있었는데, 호출부는 그대로 두고 `submit()` 헬퍼만 가짜 버킷 경유로 바꿨다.
초록불을 유지한 채로 준비한 다음에 코드를 걷어냈다 — 중간에 깨진 상태가
생기지 않게. 이제 테스트도 **실제로 쓰는 길과 같은 길**로 들어간다.

## 남은 것

환경변수 문서 정리(코드가 읽는데 `.env.example` 에 없는 것 여섯)와 단계 이름표
이중화(`progress.STAGE_LABEL` vs 화면의 `STAGE_TEXT`)는 아직이다.
