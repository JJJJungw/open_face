# RebornStudio 연동 — 무DB 잡 프로토콜

이 서비스가 RebornStudio(`sniperfactory-official/rebornstudio`)에 **컨테이너로**
붙는 방법을 적는다. 저쪽 레포는 읽기만 했고 고치지 않았다 — 저쪽에 필요한 변경은
§4 에 "요청 목록" 으로 남긴다.

## 0. 한 줄 — **계약은 페이로드다. 전송은 선택이다.**

우리는 **잡 페이로드(dict) 하나**를 받아 일한다. 서명된 URL 로 파일을 주고받고,
진행과 결과를 돌려준다. DB·버킷 이름·자격 증명은 우리 쪽에 없다.

그 페이로드를 **무엇으로 나르는지는 배포 선택**이다.

| 문 | 어떻게 | 지금 |
|---|---|---|
| **HTTP** (`service/`) | 저쪽이 우리 API 를 부른다 | **기본 경로** |
| **큐** (`msa/`) | 우리가 Redis 큐에서 꺼내 간다 | 유지 — 되돌릴 수 있게 |

**둘은 같은 러너를 쓴다** — `job_runner.run_job(job)` 하나다. 러너는 자기가 어느
문으로 들어왔는지 모른다. 그래서 문을 바꾸는 비용이 거의 0 이고, 하나를 골랐다고
다른 하나가 사라지지 않는다.

§5 의 **잡 스키마·응답·하트비트·실패 분류가 정본**이다. 아래에서 "큐" 라고 적힌
자리는 HTTP 로 읽어도 뜻이 같다 — 다른 것은 나르는 방법뿐이다.

### 왜 HTTP 를 기본으로 골랐나 (2026-08-20 결정)

1. **GPU 가 어디 있어도 된다.** 큐 경로는 우리 컨테이너가 저쪽 Redis 에 닿아야
   하니 같은 망 안이어야 한다. 우리는 AWS 에 있고 저쪽은 NCP 다.
2. **어차피 저쪽도 코드를 고쳐야 한다.** 저쪽 Step 324 는 "외부 워커가
   `q.deident` 를 소비" 가 아니라 **"자기 워커 + 인프로세스 어댑터"** 로 지어졌다
   (`reborn_transcode.deident._ADAPTERS`). 큐로 가도 저쪽 `deident_one` 을 고쳐야
   하므로 비용은 어느 쪽이든 비슷하다.
3. **라이선스.** 우리는 GPL-3.0(YOLO-FaceV2)이고 저쪽은 Apache-2.0 이다. 저쪽
   프로세스 **안에서** 임포트되는 어댑터로 붙으면 결합 저작물 해석이 걸린다.
   별도 프로세스면 네트워크 경계라 그 문제가 성립하지 않는다.

### 그 대신 지는 것

- **인증이 숙제가 된다.** 큐 경로는 인바운드 포트가 없어서 이 문제가 아예
  성립하지 않았다. HTTP 는 성립한다.
- **0대 스케일이 사라진다.** 저쪽 KEDA 가 큐 깊이로 0↔N 하는 것을 못 쓴다.
- **저쪽 Celery 슬롯이 분 단위로 묶인다.** 다만 지금도 `-c 1` 이라 실질 손해는 없다.

아래 §2-1 은 **첫 판이라 반대로 적혀 있다.** 그 근거 하나는 틀렸다 — "분 단위
작업이면 게이트웨이 타임아웃에 걸린다" 는 **동기 호출을 가정한 말**이고, 잡을 넣고
`job_id` 를 받아 폴링하는 구조에는 해당하지 않는다. 나머지(0대 스케일·인증)는
그대로 유효한 대가라서 지우지 않고 남긴다.

## 0-1. 파이썬 3.11 (2026-08-20 결정)

저쪽이 저장소 전체를 `>=3.11,<3.12` 로 묶어 두었고 워커 이미지가
`python:3.11-slim` 이다. **우리는 별도 서버라 기술적으로는 맞출 이유가 없다.**
그래도 맞춘다 — 개발과 배포가 다른 파이썬에서 도는 것이 실제로 우리를 물었기
때문이다(docs/issues/026: 3.12 에서 임포트 훅이 제거되면서 검사 하나가 조용히
아무것도 안 보게 됐다).

`pyproject.toml` 과 `.python-version` 두 곳에 적히고, 둘이 갈라지지 않는지는
`tests/test_env.py` 가 본다.

## 1. 왜 이 모양인가 — 저쪽이 이미 정해 두었다

저쪽 최신 커밋(`d723a0c`, 2026-08-10)이 트랜스코더를 그 형태로 추출했다.

그리고 `docs/design/msa-boundaries.md` 의 추출 기준표는 우리를 이름으로 지목한다.

> GPU 워커들 (Phase 4) — **M5 프로토콜로 신규 작성** … 같은 프로토콜로 셋을 더
> 찍는다 (**deidentify**·cliper·infer)

계약의 단일 출처는 `packages/reborn-contracts/queues.md` 다. 우리가 새 계약을
제안하는 것보다, 이미 1호가 돌려서 검증한 계약에 맞추는 편이 훨씬 싸다.

## 2. 경계 — 무엇이 컨테이너에 들어가고 무엇이 남는가

```
face_anonymizer/
├── core/          ← 컨테이너에 들어간다. 영상 처리 전부
├── storage/
│   ├── transfer.py  ← 들어간다. 서명된 URL GET/PUT (자격 증명 0)
│   ├── weights.py   ← 들어간다. 조달처는 §3 미결
│   ├── s3.py        ← 안 들어간다 (boto3 + 우리 열쇠 — 단독 운영용)
│   └── naming.py    ← 안 들어간다 (산출 키는 저쪽이 정해서 put_url 로 준다)
├── job_runner.py  ← 들어간다. **일 한 건**을 처리한다
├── msa/           ← 들어간다. **큐를 지켜보는 껍데기** (인바운드 포트 없음)
└── service/       ← 안 들어간다 (FastAPI 서버·자체 큐·웹 화면)
```

## 2-1. 호출은 누가 하나 — 큐 경로에서는 아무도 안 한다

> **이 절은 큐 경로(`msa/`) 얘기다.** 기본 경로는 HTTP 로 바뀌었다(§0). 지우지
> 않는 이유는 큐 경로를 유지하기로 했고, 여기 적힌 대가(0대 스케일·인증 불필요)가
> 나중에 GPU 를 NCP 로 옮길 때 다시 저울에 올라가기 때문이다.

우리 컨테이너에는 **인바운드 포트가 없다.** 저쪽이 우리를 부르는 게 아니라,
우리가 Redis 큐를 지켜보다가 잡을 스스로 꺼내 간다(밀어 넣기가 아니라 당겨 오기).

```
저쪽 API ──① 잡 넣기──▶ Redis q.deidentify ──② 꺼내기──▶ msa/celery_app
   ▲                                                          │
   │                                                     ③ run_job
   └──── default 큐 ◀── ④ 하트비트 · 완료 (토큰 첨부) ─────────┘
```

**0대까지 줄일 수 있다는 것**이 이 방향의 이유다. 저쪽 KEDA 는 큐 깊이를 보고
0↔8대를 오간다(`minReplicaCount: 0`). HTTP 였다면 받을 놈이 항상 있어야 해서 0대가
불가능하고, 로드밸런서·서비스 디스커버리·헬스체크가 전부 따라붙는다. 게다가 우리
작업은 분 단위라 요청 하나를 그만큼 붙들면 게이트웨이 타임아웃에 걸리고 그 재시도가
곧 중복 처리가 된다. 덤으로 **인바운드가 없으면 API 인증 문제도 성립하지 않는다.**

껍데기가 지는 계약은 셋이다. 태스크는 **예외를 밖으로 던지지 않는다**(던지면
celery 가 재전달하는데 저쪽도 리스로 같은 판단을 해서 같은 영상이 몇 배로 돈다).
완료 보고에는 **받았던 토큰을 그대로** 붙인다. `-c 1 --prefetch-multiplier 1` 은
취향이 아니라 계약이다 — GPU 는 한 장이고, 분 단위 작업을 쟁여 두면 컨테이너가
죽었을 때 쟁여 둔 것까지 같이 멎는다.

태스크·큐 **이름의 주인은 저쪽**이다. 저쪽이 보내는 이름과 우리가 등록한 이름이
한 글자라도 다르면 메시지는 큐에 남아 아무도 안 먹는다 — 오류도 안 난다. 그래서
전부 환경 변수로 뺐다(`face_anonymizer/msa/README.md`).

리팩토링 때 "core 는 fastapi·boto3 를 임포트하지 않는다" 로 그어 둔 선이 그대로
컨테이너 경계가 됐다. 그 선을 안 그었으면 여기서 갈라내는 데 훨씬 오래 걸렸다.

**우리 재시도·복구는 이 경로에서 쓰지 않는다.** `service/worker.py` 의 백오프
(issues/003)와 재시작 복구(issues/002)는 우리가 큐를 소유할 때의 기능이다. 저쪽
안에서는 리스·펜싱·회수를 저쪽 DB 가 하므로 같은 일을 두 곳에서 하면 서로를
방해한다. 우리는 실패를 **일시/영구로 1차 분류만** 해서 돌려준다.

## 2-2. 저쪽이 클라우드를 바꾸면 우리도 바꿔야 하나 — MSA 는 아니다

**MSA 경로는 저장소를 아예 모른다.** 페이로드에 들어오는 것은 서명된 URL 뿐이고
(`input_url`, `put_url`), 우리 쪽에는 버킷 이름도 제공자 설정도 열쇠도 없다
(§2 에서 `s3.py` 를 컨테이너 밖에 둔 것이 이것이다). 저쪽이 MinIO 에서 NCP 로
가든 그다음 어디로 가든 **서명하는 쪽만 바뀌고 우리 코드는 한 줄도 안 바뀐다.**
"저기서 고른 것이 여기도 적용되나" 의 답은, 적용할 것이 없어서 자동으로 그렇다.

단독 운영(API)은 반대다. 저장소를 **우리가** 고르므로 `FA_STORAGE_PROVIDER` 로
따로 정해 줘야 한다. 서버가 둘이니 설정도 둘이다 — 같은 곳을 보게 하는 방법은
같은 값을 양쪽에 넣는 것뿐이고, 한쪽이 고른 것을 다른 쪽이 자동으로 따라가게
하려면 설정을 내려 주는 API 가 있어야 하는데 우리 API 에는 아직 인증이 없다.
**인증 없는 서버가 저장소 설정을 받아 쓰면 아무나 우리 버킷을 바꿀 수 있다.**
그래서 지금은 환경 변수로만 정한다(`GET /api/storage` 가 읽기 전용인 이유).

### 이관 당일에 터질 것 하나 — 체크섬

botocore 1.36 부터 PutObject 에 CRC32 를 기본으로 붙이는데 **NCP 가 이걸
AccessDenied 로 거절한다.** 권한 문제가 아닌데 돌아오는 말이 똑같아서, 키와 IAM
정책과 버킷 정책을 며칠 뒤지게 되는 종류의 오류다. 저쪽 레포도 같은 이유로 같은
설정을 쓰고 있다(`apps/api-gateway/.../media/storage.py`). 우리도
`storage/s3.py:client_config()` 에서 미리 껐다 — AWS 에서도 그대로 안전하다.

## 3. 미결 — 상대와 합의해야 하는 것

### D1. 가중치를 어떻게 조달하나 ⚠️ **미결**

저쪽 워커 규약은 "자격 증명을 갖지 않는다" 인데, 우리 기본 방식은 우리 버킷에서
`FA_S3_ACCESS_KEY` 로 받는 것이다. 셋 중 하나로 가야 한다.

| 방식 | `FA_WEIGHTS_SOURCE` | 장점 | 대가 |
|---|---|---|---|
| 우리 버킷에서 받기 | `s3` **(현재 기본)** | 지금 코드 그대로. 모델 교체가 버킷 업로드 한 번 | 워커 이미지에 우리 S3 자격 증명이 들어간다 — 저쪽 규약 위반 |
| 이미지에 굽기 | `baked` | 자격 증명 0, 기동 즉시 준비 완료, 네트워크 0 | 이미지가 40MB 커지고 **모델 교체 = 재빌드·재배포** |
| 잡이 준 URL 로 받기 | `url` | 자격 증명 0, 모델 교체가 배포와 무관 | 저쪽이 `weights_url` 을 페이로드에 넣어 줘야 한다(저쪽 코드 변경) |

**지금은 `s3` 로 간다.** 우리끼리 정할 수 없는 사항이고, 정하기 전에 코드를
굳히면 나중에 되돌리는 비용이 크기 때문이다. 대신 결정을 **스위치 하나로**
남겼다 — `FA_WEIGHTS_SOURCE` 를 바꾸면 되고, 부르는 쪽(`job_runner`)은 그 사실을
모른다. 셋 다 `weights.ensure(path, url=...)` 이라는 같은 계약을 지킨다.

세 방식 모두 이미 구현돼 있다. 정해지면 기본값 한 줄과 Dockerfile 한 줄이 바뀐다.

### D2. 화질을 어느 어휘로 말하나

저쪽 트랜스코더 타깃은 `crf` 로 말하고, 우리 납품 기준은 **720p / 3500~4000 kbps
타깃 비트레이트**다. `job_runner.target_params()` 는 **둘 다 받는다** — `crf` 가
오면 우리 비트레이트 정책을 끄고 CRF 로 넘긴다. 어휘를 하나로 강제하면 붙이는
쪽이 자기 파이프라인을 고쳐야 해서, 받아 주는 쪽을 골랐다.

다만 **둘을 같이 걸면 안 된다.** 예전에 AV1 원본의 비트레이트를 그대로 상한으로
걸어 결과물이 3.4배 눌린 사고가 있었다(docs/README 의 `5fad256`). 정책은 하나만.

## 4. 저쪽에 요청할 것 (우리가 고치지 않는다)

전부 트랜스코더 것을 복사해 이름만 바꾸는 수준이다.

1. 큐 `q.deidentify` 신설 — 자원 곡선이 다르므로 별도 큐여야 한다(GPU)
2. 태스크 `deidentify_one(job)` — `transcode_one` 형판 그대로
   (`acks_late`, `reject_on_worker_lost`, `ignore_result`)
3. DB 쪽 짝 셋 — `build_jobs`(상태 전이+토큰+리스+presign) ·
   `deidentify_heartbeat` · `deidentify_complete`(펜싱 판정)
4. 회수 스윕 — 리스 만료를 pending 으로 되돌리는 짝
5. KEDA ScaledObject — `listName: q.deidentify`, min 0
6. `queues.md` 에 우리 잡 스키마 등재 (§5)
7. D1 이 `url` 로 정해지면 페이로드에 `weights_url` 추가
8. **`review_needed` 를 저장하고 검수로 라우팅** — 비식별화가 안 된 영상이
   '완료' 로 넘어가는 것을 막는 유일한 지점이다(§5, docs/issues/008)
9. 잡 하나에 **타깃 하나** — 우리는 타깃마다 검출을 다시 돌려서 GPU 를 배로 쓴다
10. `terminationGracePeriodSeconds` 를 넉넉히(600초) — 한 편이 분 단위다
11. **페이로드에 `batch_id` 와 `name` 을 넣어 주세요** — 로깅 때문이다(§8).
    없어도 처리는 된다. 다만 그 둘이 없으면 "이 폴더 몇 시에 시작해서 몇 시에
    끝났나" 와 "K_00297.mp4 가 언제 처리됐나" 에 **나중에 아무도 답할 수 없다.**
    소급이 안 되는 종류의 손실이라 먼저 요청한다.
12. 완료 보고의 `worker_avg_s` 로 남은 시간을 계산해 주세요 — 큐 깊이는 저쪽만
    알고 처리 속도는 우리만 안다(§8).
13. 하트비트의 `percent` · `stage_label` · `eta_s` 를 저장해 주세요 — 처리
    중인 영상에 대해 화면이 그릴 수 있는 값은 이것뿐이다(§5). 실패 화면에는
    `error` 말고 `problem.title` · `problem.hint` 를 띄워 주세요.

## 4-0. 클라우드 접근은 **이쪽이 맡는다** (2026-08-20 결정 — 방향 전환)

앞의 §0~§3 은 "저쪽이 서명하고 우리는 URL 만 받는다" 를 전제로 쓰였다.
**그 전제가 뒤집혔다.**

| | 예전 전제 | 지금 |
|---|---|---|
| 자격 증명 | 저쪽 `.env` 하나 | **우리 `.env`** |
| 잡에 실리는 것 | presigned GET/PUT | **입력 경로 · 출력 경로** |
| 서명하는 쪽 | 저쪽 `build_jobs` | **우리 `service/remote.resolve`** |

**러너는 안 바뀌었다.** 경로를 서명된 URL 로 바꾸는 일을 **문 하나에서** 하기
때문이다(`remote.resolve`). 그래서 `job_runner.run_job` 은 예전과 똑같이 URL 두
개만 보고, 저쪽이 직접 서명해 보내는 방식도 **그대로 받는다** — 둘 다 같은 곳으로
합류한다. 이 전환의 값이 그것이다: 방향이 뒤집혔는데 러너·진행률·실패 분류·검수
판정이 한 줄도 안 바뀌었다.

### 저쪽이 보내는 것

```json
{"video_id": "uuid", "token": "펜싱 토큰",
 "input_key": "work/<video_id>/analysis-720p.mp4",
 "targets": [{"label": "deid-720p", "height": 720,
              "output_key": "work/<video_id>/analysis-720p.deid.mp4"}]}
```

`s3://버킷/키` 도 받는다(입력이 스테이징, 결과가 납품 버킷인 구성). 필드 이름은
넉넉히 본다 — `input_key`·`input_path`·`input`·`source_key`·`source` 와
`put_key`·`output_key`·`output_path`·`output`. 이름 하나가 어긋났을 때 나는
오류가 "input_url 이 필요합니다" 면 무엇이 잘못됐는지가 안 드러난다.

### 붙이기 전에 칠 것 — `GET /api/credentials/health`

```json
{"ok": true, "credentials": {"source": "환경 변수 (AWS_ACCESS_KEY_ID)", "present": true},
 "provider": "s3", "bucket": "…", "read": true, "write": true, "checked_ms": 143}
```

**읽기와 쓰기를 따로 본다.** 읽기만 되는 자격 증명이 흔하고, 그 둘은 사람이 할
일이 다르다(정책에 `s3:PutObject` 를 더하는 일이다). 안 되면 503 과 함께
`problem.title`·`hint` 가 온다 — 키 없음 / 키 틀림 / 권한 없음 / 버킷 없음 /
못 닿음이 각각 다른 딱지다(issues/025).

### 서명은 **접수할 때** 한다

스레드 안에서 서명하면 실패가 202 뒤에 숨는다. 저쪽은 잡을 받았다고 믿고 폴링을
시작하고, 경로 오타 하나가 **리스 만료까지 안 드러난다.** 그래서 경로가 없거나
저장소가 설정 안 돼 있으면 그 자리에서 400 이다.

## 4-1. HTTP 문 — 저쪽이 실제로 부르는 방법 (구현됨)

`service/remote.py` · 라우트 둘. **새 처리 로직이 없다** — `job_runner.run_job` 을
그대로 부른다. 큐 경로와 페이로드가 같으므로 §5 가 그대로 정본이다.

```
POST /api/deident/jobs         잡 하나 (§5 스키마)  →  202 {job_id, status}
GET  /api/deident/jobs/{id}    진행·결과            →  200
헤더: X-Deident-Token: <FA_REMOTE_TOKEN>
```

**동기로 붙들지 않는다.** 한 편이 분 단위라 요청을 그만큼 붙들면 게이트웨이가
먼저 끊고, 그 재시도가 곧 중복 처리가 된다. 넣고 `job_id` 를 받아 폴링한다.

`GET` 응답은 상태에 따라 다르다.

```json
{"job_id": "…", "video_id": "…", "status": "running",
 "progress": {"elapsed_s": 3.0, "percent": 46.2, "stage": "detect",
              "stage_label": "얼굴 찾는 중", "eta_s": 21}}
```

`status` 가 `done` 이면 `result` 에 §5 응답이, `failed` 면 `error`·`transient`·
`stage`·`problem` 이 실린다 — 큐 경로가 완료 메시지에 싣던 것과 **같은 짝**이다.

### 하트비트를 우리가 밀지 않는다

큐 경로는 리스 연장 메시지를 보내야 해서 밀었다. HTTP 에서는 부르는 쪽이 이미
붙어 있으므로 **당겨 간다.** 같은 값이 `progress` 에 실리고, 저쪽은 그걸 그대로
`deident_heartbeat` 로 넘기면 리스가 연장된다.

### 바쁘면 429 — 대기열을 만들지 않는다

`FA_REMOTE_MAX_INFLIGHT`(기본 1 — GPU 한 장) 를 넘으면 거절한다. 우리가 대기열을
만들면 **큐가 둘이 된다.** 저쪽은 이미 리스·펜싱·회수·재시도 상한을 갖고 있고,
두 곳이 각자 판단하면 같은 영상이 몇 배로 돈다. 우리는 "지금 못 받는다" 만
정확히 말하고 언제 다시 줄지는 저쪽이 정한다.

### 문은 기본으로 활짝 열려 있지 않다

`FA_REMOTE_TOKEN` 이 비어 있으면 **같은 기계에서만** 열린다. 오픈소스로 받아
자기 노트북에서 돌리는 사람은 설정 없이 쓰고, 밖에서 부르려면 토큰을 채워야
한다. 망으로 막는 것(보안 그룹)은 1층이고 토큰은 2층이다 — 겹치기가 아니다
(§2-3).

### 저쪽에 필요한 변경

지금 저쪽 `deident_one` 은 자기 안에서 `run_deident_job` 을 부른다. 그 자리를
**우리 API 호출로 바꾸면 된다.** 잡 페이로드(`build_jobs` 가 이미 만드는 것)를
그대로 body 로 보내고, `job_id` 로 폴링하다가 끝나면 `deident_complete` 로
넘기면 된다. `_ADAPTERS` 와 `run_deident_job` 은 이 경로에서 안 쓰인다.

## 5. 잡 스키마 (제안)

```json
{
  "video_id": "uuid",
  "token": "펜싱 토큰 — 완료 보고에 그대로 되돌린다",
  "input_url": "presigned GET (TTL 4h)",
  "targets": [
    {"label": "deid-720p",
     "height": 720,
     "bitrate": "3500k", "max_bitrate": "4000k",
     "method": "mosaic", "conf": 0.25, "imgsz": 1280,
     "put_url": "presigned PUT", "content_type": "video/mp4"}
  ],
  "weights_url": "(D1 이 url 로 정해질 때만)",
  "heartbeat_every_s": 60,
  "batch_id": "kbs-0813",
  "name": "K_00297_원본.mp4"
}
```

`batch_id` 와 `name` 은 **처리에 쓰지 않는다.** 기록에만 쓴다(§8). 없으면
`name` 자리에 `video_id` 를 넣고 묶음은 비워 둔 채 돈다. 필드 이름이 이미 다른
것으로 정해져 있다면 알려 주세요 — `batch` · `group_id` · `folder` 도 알아듣게
해 두었습니다(`msa/journal.py: BATCH_KEYS`).

`height: null` 은 스케일 생략(업스케일 금지) — 저쪽 트랜스코더와 같은 뜻이다.
키가 아예 없는 것과 다르므로 `target_params()` 가 따로 구분한다.

응답:

```json
{"elapsed_s": 41.2,
 "review_needed": false,
 "review": [],
 "notices": [],
 "started_at": "2026-08-13T01:04:37+09:00",
 "finished_at": "2026-08-13T01:05:18+09:00",
 "span": "8월13일 01시04분 ~ 01시05분 (41.2초)",
 "batch_id": "kbs-0813",
 "worker_avg_s": 40.7,
 "targets": [{"label": "deid-720p", "frames": 5828, "detected_frames": 5102,
              "detection_rate": 0.8754, "realtime_factor": 4.7,
              "warnings": []}]}
```

산출 키는 저쪽이 결정론적으로 아는 값이라 되돌리지 않는다.

### 하트비트 — 화면이 그릴 수 있는 유일한 진행 정보

```json
{"video_id": "uuid", "token": "…", "progress_s": 18.4,
 "percent": 46.2, "stage": "detect", "stage_label": "얼굴 찾는 중",
 "eta_s": 21}
```

60초마다(`heartbeat_every_s`) 간다. **원래 목적은 리스 연장 하나였는데 진행률을
얹었다.** 화면이 그릴 수 있는 값 중 우리만 아는 것이 이것뿐이기 때문이다 —
목록·순번·남은 건수는 전부 저쪽이 안다. 이게 없으면 처리 중인 영상에 대해
화면은 스피너까지밖에 못 그린다.

`percent` 는 **전체 대비**다. 단계별이 아니다 — 단계별로 주면 검출 100% 다음에
렌더 0% 가 와서 진행바가 되감긴다. 그리고 **절대 줄지 않는다.** 단계가 통째로
건너뛰어질 수 있고(h264 원본이면 전사가 없다) 콜백이 늦게 도착할 수도 있는데,
그때 뒤로 가느니 조금 부정확한 편이 낫다.

`eta_s` 는 5% 아래에서는 `null` 이다. 그 구간에서는 추정이 요동쳐서 "남은 시간
47분" 이 떴다가 곧 3분이 된다. `null` 이면 '계산 중' 으로 띄워 주세요.

`stage_label` 은 화면에 그대로 띄울 한국어다. `stage` 는 기계용 코드고 —
`download` · `transcode` · `detect` · `track` · `render` · `upload` 여섯 개다.

### 실패 — 화면에 띄울 얼굴이 따로 있다

```json
{"ok": false, "stage": "download", "transient": true,
 "error": "내려받기 실패 HTTP 403",
 "problem": {"code": "download", "retryable": true,
             "title": "원본을 내려받지 못했습니다",
             "hint": "서명 URL 이 만료됐을 수 있습니다. 다시 발급하면 됩니다",
             "detail": "내려받기 실패 HTTP 403"}}
```

`error` 는 **우리 내부 문구**다. 화면에 그대로 뿌리면 사용자가 볼 말이 아니다.
`problem.title` 과 `problem.hint` 를 띄워 주세요. 기존 `error`·`stage`·
`transient` 는 그대로 두었으니 이미 읽고 있다면 안 고쳐도 됩니다.

### review — 처리는 됐지만 사람이 봐야 하는 경우 ⚠️

**`ok=true` 와 함께 온다. 실패가 아니다.** 얼굴이 하나도 안 잡히면 원본이 그대로
나가는데, 그게 풍경 영상이라 정당한 0 인지 설정이 틀려서 0 인지는 코드가 구분할
수 없다(docs/issues/008).

```json
{"review_needed": true,
 "review": [{"code": "no-detections",
             "detail": "no-detections",
             "message": "얼굴이 하나도 검출되지 않았습니다. 원본이 그대로 나갔습니다 — 얼굴이 없는 영상이 맞는지 한 번 확인해 주세요."}]}
```

`code` 는 `no-detections` · `low-detection-rate` · `decode-partial` ·
`decode-short` 넷 중 하나다. `notices` 는 같은 모양이지만 사람을 부를 일은 아닌
것들(`audio` · `decode-unverified`)이다.

**저쪽에 필요한 것**: `review_needed` 가 참이면 `done` 으로 넘기되 검수 대기로
표시해 주세요. 재시도는 의미가 없습니다 — 다시 돌려도 결과가 같습니다.

## 6. 실패 분류

워커가 1차 분류만 하고, 판정(재시도할지·상한이 얼마인지)은 저쪽 `complete` 한
곳에서 낸다. 몇 번까지 해볼지는 우리가 알 수 있는 정보가 아니다.

| 상황 | `transient` | 왜 |
|---|---|---|
| 네트워크 오류·5xx·429·408 | ✅ | 다음에는 될 수 있다 |
| **403** | ✅ | presign 만료와 권한 거부를 응답만으로 구분할 수 없다. 만료라면 재큐잉이 새 URL 을 준다 |
| 그 밖의 4xx | ✗ | URL 이 틀렸거나 정책이 막는다 |
| 가중치 조달 실패 | ✅ | 이 영상의 문제가 아니다. 영구로 두면 큐 전체가 상한까지 태워진다 |
| 검출기 로드 실패 | ✅ | 같은 이유 |
| 파이프라인 실패(깨진 파일·잘못된 인자) | ✗ | 같은 입력이면 같은 결과다 |
| 진행 정체 300초 | ✅ | 환경 문제일 수 있다 |

### 정체 감시를 스레드로 두지 않은 이유

저쪽 트랜스코더는 인코딩을 스레드에서 돌리고 본 스레드가 정체를 보다가 ffmpeg
프로세스를 끊는다. 우리는 진행 콜백 안에서 시간으로만 본다.

스레드를 쓰면 멎은 ffmpeg 도 끊을 수 있지만, **데몬 스레드를 남긴 채 임시
디렉터리를 지우게 되어 더 나쁜 상태**가 된다. 콜백이 아예 안 오는 종류의 멈춤은
저쪽 **리스 만료 → 회수 → 재전달**이 처리하고, 뒤늦게 끝난 우리 보고는 펜싱
토큰이 걸러 낸다. 저쪽 설계가 이미 그 경우를 전제하고 있다("중복 실행은 complete
의 펜싱이 버린다").

## 6-1. 실제로 돌려 봤다

### 브로커에 실제로 붙여 한 바퀴 — ✅ 확인함

Redis 하나 띄우고, 저쪽 `build_jobs`(발신)와 `heartbeat`/`complete`(수신)를 흉내
내는 프로세스를 세워 **우리 워커를 그대로** 돌렸다. 바꾼 것은 검출기 하나뿐이다
(가중치·GPU 없이 배선을 보는 게 목적).

| 넣은 것 | 나온 것 |
|---|---|
| 정상 잡 | `ok=true elapsed_s=1.6` · 하트비트 1건 · PUT 로 H.264 결과물 도착 |
| **남의 토큰**으로 온 보고 | 저쪽이 대조해서 **버림** — 펜싱이 실제로 작동한다 |
| 입력 URL 403 | `transient=true stage=download` (presign 만료로 본다) |
| 출력 URL 404 | `transient=false stage=upload` (다시 해도 같다) |
| 출력 URL 503 | `transient=true stage=upload` |
| 연결 거부 | `transient=true stage=upload` |

결과물을 ffprobe 로 확인: `h264 · 320x240 · 15fps · 45프레임 · 3.0초`. 프레임
수가 원본과 같고 코덱이 바뀌었다 — 파이프라인이 큐 경로에서도 그대로 돈다.

### 그 과정에서 나온 것 — Redis 에는 ack 가 없다

`acks_late` 는 컨테이너가 죽으면 메시지가 다시 배달되는 근거인데, **Redis
브로커에는 ack 자체가 없다.** kombu 가 `visibility_timeout` 으로 흉내 낼 뿐이고
기본값이 3600초다. 그래서 컨테이너를 강제 종료하면 celery 기준으로는 **한 시간
뒤에야** 되살아난다.

실제 회수는 저쪽 **리스 만료 스윕(5분)** 이 한다 — 하트비트가 멎으면 저쪽이
되돌려 다른 워커에게 준다. 즉 **회수의 주인은 celery 가 아니라 저쪽 리스**이고,
`visibility_timeout` 은 그 뒤를 받치는 안전망이다. 짧게 잡으면 오히려 멀쩡히
돌고 있는 작업이 중복 배달돼 GPU 를 두 배로 쓴다. 명시적으로 3600 을 넣고 그
이유를 코드에 적었다(`msa/config.py`).

## 2-3. 인증 — HTTP 경로에서 새로 생기는 숙제

큐 경로에는 없던 문제다. 인바운드 포트가 없으면 "누가 부르나" 가 성립하지 않는다.
HTTP 로 가면 성립한다.

**저쪽 로그인은 이 자리를 못 덮는다.** 저쪽 로그인은 **사람이 저쪽에** 들어가는
것이고, 우리를 부르는 것은 사람이 아니라 저쪽 Celery 워커다 — `dispatch_deidents`
가 30초 주기로 혼자 돈다. 그 순간 세션도 JWT 도 없다. **담을 인증 정보가 없는
것이지, 이미 담겨 있는데 굳이 하나 더 만드는 게 아니다.**

방향(2026-08-20): **서비스 전체에 토큰 하나.** 연동 전용 토큰을 따로 두지 않는다 —
기계 하나로 사람 문과 기계 문이 같이 닫힌다.

- **검사는 라우트에서 한다.** 첫 페이지에서만 막으면 `curl` 로 그냥 들어온다.
  화면이 잠긴 것과 API 가 잠긴 것은 다르다.
- **첫 페이지는 그 토큰을 사람이 넣는 자리**일 뿐이다.
- **비어 있으면 루프백에서만 열린다.** 오픈소스로 받아 자기 노트북에서 돌리는
  사람은 설정 없이 바로 쓰고, 외부 IP 로 들어오면 거부한다. 저쪽이
  `_enforce_prod_secrets` 로 "운영에서 기본값이면 기동 거부" 를 해 둔 것과 같은
  자세인데, 처음 받는 사람을 안 막는다는 점만 다르다.
- **평문 http 로는 받지 않는다.** 잡 페이로드의 `input_url`·`put_url` 은 저쪽
  버킷에 대한 **읽기·쓰기 권한 그 자체**다. 클라우드가 갈려 공용 인터넷을 타므로
  평문이면 그 열쇠가 경로 위에 그대로 보인다.

**망으로 막는 것이 1층이다** — 저쪽 서버 IP 만 열고 나머지는 닫는다. 토큰은 그
위에 얹는 2층이고, 겹치기가 아니다: **SSRF 는 IP 필터를 통과한다.** 저쪽은
서명된 URL 을 끊임없이 가져오는 시스템이라 "이 URL 을 가져와라" 를 조작할 수 있는
구멍이 하나라도 나면 그 요청은 **저쪽 서버 IP 로** 우리에게 온다. 그렇게 만들어진
요청에는 헤더를 붙일 수 없다.

한계는 적어 둔다. **토큰 하나는 "누가 했는지" 를 모른다.** 비식별화는 관리자가
돌리고 결과를 라벨러에게 넘기는 구조라(사용자 확인 2026-08-20) 지금은 과하지 않은
선택이다. 라벨러 단위 추적이 필요해지면 저쪽 로그인에 얹는 쪽으로 가야 한다.

## 8. 로깅 — 목적은 같고 구조는 다르다

로그가 답해야 하는 질문은 어느 경로든 똑같다. 언제 시작해 언제 끝났나(한국
시각) · 얼마나 걸렸나 · 얼굴은 몇 프레임에서 잡혔나 · 사람이 봐야 할 건이 있나 ·
실패했다면 어느 단계에서.

**그런데 두 경로가 사는 곳과 아는 것이 달라서, 구조를 하나로 합칠 수 없다.**

|  | API (`service/`) | MSA (`msa/`) |
|---|---|---|
| 남는 곳 | 파일 (EC2 에 계속 떠 있다) | 파일 **+ stdout** — 컨테이너는 지워진다 |
| 되읽기 | `GET /api/events` | 없다. 로그 수집기가 걷어 간다 |
| 파일별 시작/종료 | 우리가 낸다 | 우리가 낸다 |
| 폴더 시작/종료 | 우리가 낸다 (`/api/batches`) | **못 낸다** — 아래 참고 |
| 남은 시간 | 우리가 낸다 (큐가 우리 것) | **반만** 낸다 — `worker_avg_s` |
| 화면 | `static/index.html` | 없다 |

기록의 **모양**은 하나다. 같은 `events.py` 저널에 같은 스키마로 쌓이고, 줄마다
`"mode": "api" | "msa"` 가 붙어 어느 얼굴이 처리했는지 구분된다. 시각 표기도
같은 `timefmt` 를 써서 두 경로가 같은 문장을 낸다.

### 폴더 집계를 우리가 못 내는 이유

KEDA 가 컨테이너를 여러 대로 늘리면 **같은 폴더의 영상이 여러 컨테이너로
흩어진다.** 한 컨테이너는 자기가 처리한 것만 보므로 "폴더 전체가 몇 시에 시작해
몇 시에 끝났나" 를 알 수 없다. 큐 깊이도 마찬가지로 저쪽 것이다.

그래서 역할을 이렇게 나눈다. **우리는 줄마다 `batch_id` 를 빠짐없이 남기고,
집계는 전부를 보는 쪽이 한다.** 이건 성능 문제가 아니라 관측 범위 문제라서,
컨테이너를 아무리 고쳐도 우리 쪽에서 해결되지 않는다.

`batch_id` 가 페이로드에 안 들어오면 그 파일은 **어떤 폴더 집계에도 안 잡힌다.**
나중에 소급할 수 없다 — 그래서 §4-11 로 먼저 요청한다.

### 남은 시간을 반만 내는 이유

남은 시간 = 큐 깊이 × 평균 처리 시간이다. **큐 깊이는 저쪽만 알고, 평균 처리
시간은 우리만 안다.** 우리가 넘겨짚어 계산하면 틀린 값이 화면에 뜬다.

그래서 완료 보고에 `worker_avg_s`(이 워커의 최근 20건 평균)를 실어 보낸다.
표본이 없으면 **0 이 아니라 `null`** 로 보낸다 — 0 을 보내면 화면에 "남은 시간
0분" 이 뜨고, 그건 모른다는 뜻이 아니라 다 끝났다는 뜻으로 읽힌다.

### 컨테이너 수명도 기록한다

`worker.ready` 에 **콜드스타트 시간**이, `worker.stopped` 에 그 컨테이너가 처리한
건수·실패·평균이 남는다. KEDA 가 0↔N 을 오가므로 "잡을 넣었는데 왜 늦게
시작하냐" 의 첫 용의자가 콜드스타트이고, 처리 도중에 종료된 흔적이 보이면
`terminationGracePeriodSeconds` 가 짧다는 신호다(§4-10).
